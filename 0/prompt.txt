## 1. `michi-toon` (`/Users/gabe/Projects/michi/crates/michi-toon/src/`)

**Purpose:** Renders a flat, tabular list of rows into the TOON text format — a header line (`type_name[count]{field,field,...}:`) stating field names once, followed by comma-separated rows. Also does the reverse for `serde`-serializable structs when the `serde` feature is on.

**Public API:**
- `pub struct Value` (enum): `Str(CompactString)`, `Int(i64)`, `Float(f64)`, `Bool(bool)`, `Null`. `From&lt;&amp;str|String|CompactString|Cow&lt;str&gt;|i32|u32|i64|u64|usize|f32|f64|bool|Option&lt;String&gt;&gt;` impls. `Display`.
- `pub struct ToonOptions { type_name, fields: Vec&lt;String&gt;, rows: Vec&lt;Vec&lt;Value&gt;&gt;, total_count: Option&lt;usize&gt;, hints: Vec&lt;String&gt;, max_cell_len: usize }` (`#[non_exhaustive]`), builder methods `new()`, `.total_count()`, `.hints()`, `.max_cell_len()` (default 200), and `.validate() -&gt; Result&lt;(), ToonError&gt;` — **opt-in**, not called automatically by `render_toon()`.
- `pub fn render_toon(opts: &amp;ToonOptions) -&gt; String` — never errors; sanitizes bad input in place (structural chars in headers/hints are replaced with `_`) rather than rejecting it.
- `pub enum ToonError { InvalidTypeName, InvalidFieldName, RowLengthMismatch, InvalidItem }`.
- `pub fn escape_value(v: &amp;str) -&gt; Cow&lt;str&gt;` / `escape_value_quoted(v: &amp;str) -&gt; String`.
- `#[cfg(feature = "serde")] pub fn list&lt;T: Serialize&gt;(type_name, items: &amp;[T]) -&gt; Result&lt;String, ToonError&gt;` — serializes each item via `serde_json::to_value`, requires the result be a JSON object (struct/map); scalars/arrays error with `InvalidItem`.

**Cargo features:** `default = []` (zero deps beyond `compact_str`, which is a mandatory dep, not feature-gated). `serde = ["dep:serde", "dep:serde_json"]` — required for `toon::list()`. `schemars` — derives `JsonSchema` on `ToonOptions`/`Value`.

**Usage patterns (from examples/tests):**
- Manual construction: build `ToonOptions` by hand with typed `Value` rows (the `examples/basic_toon.rs` / README pattern) — this is the primary intended path for a CLI tool with already-structured data.
- `toon::list()` for "I have a `Vec&lt;MySerdeStruct&gt;`, just render it" (needs `serde` feature). Field order comes from the first non-empty item's serialized key order (`serde_json::to_value` with the workspace's `preserve_order` feature enabled, so struct field order is preserved, not alphabetized).
- Long cell strings are auto-truncated per-cell via `michi_truncate::truncate_inline` when they exceed `max_cell_len`, embedding the `(N chars truncated — use full=true)` marker inline in the cell.

**Important gaps for a downstream consumer (verified, not guessed):**
- **No nested/table structures.** TOON itself (per `docs/spec/02-toon-format.md`'s grammar) is strictly one header + flat rows — no nested TOON blocks. In `toon::list()`, a struct field that's an array/object gets JSON-stringified and dropped into a single quoted cell (confirmed by test `list_stringifies_nested_values_losslessly`: `tags: Vec&lt;String&gt;` becomes cell value `"[\"a\",\"b\"]"`). There is no recursive/multi-table TOON renderer.
- **No parser in the public API**, despite the crate's own `Cargo.toml` description saying "renderer and parser." The only TOON parser in the repo is `tests/support/toon_parser.rs`, explicitly documented as "Test-only ... NOT part of the public API ... not a general-purpose TOON parser for untrusted input." `ARCHITECTURE.md`'s mention of a "`ToonSerializer`" type is also aspirational/inaccurate — no such type exists in `src/`.
- Row length is not validated by `render_toon()` itself — mismatches are silently rendered (missing cells → empty; the `#[cfg(debug_assertions)] debug_assert!` in `render.rs` would panic in debug builds, but that's dev-only). Call `.validate()` explicitly if you need hard errors.

**Dependencies on siblings:** depends on `michi-truncate` (for per-cell truncation). Depends on nothing else in the workspace.

## 2. `michi-truncate` (`/Users/gabe/Projects/michi/crates/michi-truncate/src/lib.rs`)

**Purpose:** Truncate a string to at most N Unicode **scalar values (chars)** — not bytes, not model tokens — at a UTF-8 char boundary, appending a human/agent-readable marker describing what was cut and how to get the rest.

**Public API (the entire crate is ~90 lines of non-test code):**
```rust
pub struct Truncated {
    pub content: String,
    pub original_len: usize,      // original BYTE length (not char count)
    pub was_truncated: bool,
    pub signal: Option&lt;String&gt;,   // the marker text actually embedded in `content`
}

pub fn truncate(content: &amp;str, max_chars: usize, hint: &amp;str) -&gt; Truncated;
pub fn truncate_inline(content: &amp;str, max_chars: usize, hint: &amp;str) -&gt; String; // == truncate(...).content
```

**Algorithm (exact, confirmed by reading the code):**
- Fast-path: if `content.len() &lt;= max_chars` (byte length), return unchanged (byte length ≥ char count, so this implies char count also fits) — `was_truncated: false`, `signal: None`.
- Otherwise compute real `char_count`; if that's also `&lt;= max_chars`, still unchanged.
- Otherwise: build suffix `" ({char_count} chars truncated — use {hint})"`, compute how many content chars can be kept (`max_chars - suffix_chars`, saturating), slice at that char boundary via `char_indices().nth(...)`, append the suffix, then hard-cap the whole result to `max_chars` chars again in case the suffix alone is longer than `max_chars` (tiny `max_chars` or long `hint` string) — trims via char boundary, never mid-codepoint.
- `signal` is recomputed from what's *actually* left in `content` after the hard-cap (trimmed of leading space) — `None` if there was no room for any signal text, otherwise guaranteed to literally appear in `content`.

**Answering the task's specific questions:**
- Unit is **chars (Unicode scalars)**, not bytes and not LLM tokens — there is no tokenizer dependency anywhere in this crate or workspace (`Cargo.toml` has zero `[dependencies]`).
- Truncation marker: yes, `" ({n} chars truncated — use {hint})"`, caller-supplied `hint` string (e.g. `"full=true"`) is meant to tell the agent how to get the untruncated content (e.g., a param name to pass on the next call).
- Return value: `Truncated` struct with the content **and** metadata (`original_len`, `was_truncated`, `signal`) — not just a bare string. `truncate_inline()` is a convenience that discards the metadata and returns only the string (this is what `michi-toon`'s per-cell truncation calls).

**Cargo features:** none; `default = []`, zero dependencies.

**Note:** `PRINCIPLES.md` sketches a hypothetical future `TruncationOutcome&lt;T&gt;` / `truncate_by_count` / `truncate_by_bytes` API as a *worked example of design philosophy* ("split the decision from the signal") — **this is not implemented**. Don't mistake it for shipped API; the only truncation primitive that exists today is the char-based `truncate()`/`truncate_inline()` above.

**Dependencies on siblings:** none — this is the most upstream crate; everything else depends on it (directly or transitively).

## 3. `michi-resilience` (`/Users/gabe/Projects/michi/crates/michi-resilience/src/lib.rs`)

**Purpose:** Pure math/parsing for retry decisions — **not** an actual retry executor, HTTP client wrapper, or circuit breaker. It computes "how long should I wait before retry N" and parses `Retry-After`; the caller still owns the actual retry loop.

**Public API:**
```rust
pub struct RetryConfig { pub max_retries: u32, pub base_delay: Duration, pub max_delay: Duration, pub jitter_factor: f64 } // #[non_exhaustive]
impl RetryConfig {
    pub fn new(max_retries, base_delay, max_delay, jitter_factor) -&gt; Self;        // clamps invalid inputs silently
    pub fn try_new(...) -&gt; Result&lt;Self, RetryConfigError&gt;;                        // strict, errors on invalid inputs
}
impl Default for RetryConfig; // max_retries=3, base_delay=500ms, max_delay=30s, jitter_factor=0.2

pub enum RetryConfigError { MaxDelayIsZero, BaseDelayExceedsMaxDelay{base,max}, JitterFactorOutOfRange{factor} }

pub fn next_retry_delay(config: &amp;RetryConfig, attempt: u32, jitter_seed: f64, retry_after: Option&lt;Duration&gt;) -&gt; Option&lt;Duration&gt;;
// None once attempt &gt;= max_retries. jitter_seed is caller-supplied random [0,1] — crate has no RNG dependency.
// Delay = max(exponential-backoff-with-jitter, retry_after), capped at max_delay.

pub fn parse_retry_after(header_value: &amp;str) -&gt; Option&lt;Duration&gt;;                  // RFC 7231 Retry-After: seconds or HTTP-date
pub fn parse_retry_after_at(header_value: &amp;str, now: SystemTime) -&gt; Option&lt;Duration&gt;; // testable variant, explicit "now"
pub fn is_retryable_status(status: u16) -&gt; bool;  // true only for 429, 502, 503, 504 (NOT 500 — deliberate, tested)

pub struct IdempotencyKey(pub String);
impl IdempotencyKey {
    pub fn new(s: impl Into&lt;String&gt;) -&gt; Self;
    pub fn as_str(&amp;self) -&gt; &amp;str;
    pub fn from_hash(operation: &amp;str, data: &amp;[u8]) -&gt; Self;  // FNV-1a 64-bit hash, formatted "{operation}:{hash:016x}"
}
// From&lt;String&gt;, From&lt;&amp;str&gt; also implemented.

pub enum AlreadyDone { Yes { result: String }, No } // #[non_exhaustive]
pub fn already_done(stored: Option&lt;String&gt;) -&gt; AlreadyDone;
pub fn render_already_done(operation: &amp;str, summary: &amp;str, hints: &amp;[String]) -&gt; String;
```

**Cargo features:** none; `default = []`, zero dependencies at all (`[dependencies]` section is empty).

**Usage pattern:** caller supplies its own RNG for `jitter_seed`, its own HTTP client, and its own storage for idempotency lookups; this crate just does the arithmetic/parsing/formatting around those. `is_retryable_status` deliberately excludes 500 (documented reasoning in a test: "500 is a server bug — retrying reproduces it and risks duplicate side effects on writes").

**No circuit breaker, no async, no actual retry loop.** `docs/spec/06-decisions.md` confirms this is intentional: an async `CircuitBreaker` and retry-wrapper are explicitly deferred to a future, not-yet-built `pipeline` crate (which would depend on tokio) — they are called out as *not* belonging in `michi-resilience` because that crate must stay dependency-free and sync.

**Dependencies on siblings:** none.

## Practical implications for monokl

1. **Reuse `michi-toon::{ToonOptions, Value, render_toon}` directly** for any tabular/list agent output monokl needs — it's a complete, tested implementation matching the format monokl's spec presumably already targets (michi's own `docs/spec/02-toon-format.md` is the TOON grammar). Don't hand-roll TOON escaping/truncation — `escape_value`, `sanitize_header_token` and the max-cell-len truncation logic already handle the edge cases (commas, quotes, newlines, NaN/Inf floats, structural chars in headers).
2. **`michi-core::response::AgentResponse`** is the highest-leverage single reuse point if monokl wants a unified builder for TOON-list-or-KV output plus hints/recovery/error/MCP-result assembly — it composes nearly everything else in the workspace.
3. **`michi-core::error::DomainError`** is a ready-made typed error model (code/class/hints/recovery/retryable/retry_after) with three render targets (agent text, GitHub Actions annotation, JSON) and an MCP `CallToolResult` conversion — likely reusable wholesale rather than reinventing monokl's own error-rendering.
4. **`michi-truncate::truncate`** truncates by **character count**, not tokens or bytes — if monokl needs actual LLM-token-budget truncation, this crate does not provide that; it would need to be layered on top (e.g., feed a token-estimated char budget into `truncate()`).
5. **`michi-resilience`** gives retry-delay math and `Retry-After` parsing only — if monokl needs an actual retry-executing HTTP wrapper or a circuit breaker, that does not exist yet anywhere in this workspace (explicitly deferred to a future `pipeline` crate per `docs/spec/06-decisions.md`).
6. **No TOON parser exists as public API** — if monokl needs to *read* TOON (not just emit it), that would have to be written new; michi does not supply it despite package descriptions implying otherwise.
7. **Not yet on crates.io** — monokl would depend via git tag (`michi = { git = "https://github.com/orin-axi/michi", tag = "v0.1.0" }`, plus corresponding `michi-core`/`michi-toon`/etc. path deps are internal so a single top-level `michi` git dep should suffice) per the project's own stated interim recommendation, and per `PRINCIPLES.md`, monokl adopting it for real would itself count as the "real consumer integration" that's gating the eventual crates.io release.</result>
