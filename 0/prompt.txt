## Findings

**libclang FFI is real and production-precedented, but genuinely breaks the no-toolchain rule.** `clang-sys` (KyleMayes) is the real FFI layer — actively maintained (pushed 2026-02-25, 26 open issues, 160 stars) — and `bindgen` literally depends on it (confirmed via crates.io: bindgen 0.72.1's deps include `clang-sys` directly). But bindgen's own docs require Clang 9.0+ and document `LIBCLANG_PATH`/`llvm-config` discovery explicitly, and the friction is real, not hypothetical: rust-bindgen#1797, #2091, #1276, #1579, #2360, #1411 and clang-sys#74 are all live "could not find libclang" reports spanning Windows, Docker, and Alpine, plus actions/runner-images#3316 for GitHub Actions Windows runners. This is a well-worn pain point for exactly the "cargo install and just works" experience monokl wants.

There IS a better-fitting crate than bindgen for monokl's actual need ("parse and walk a tree," not "generate FFI bindings"): **`clang-ast`** by dtolnay — real and very actively maintained (pushed 2026-06-24, only 2 open issues, 575k downloads). It doesn't link libclang via FFI at all; instead you shell out to `clang -Xclang -ast-dump=json -fsyntax-only` yourself and clang-ast just deserializes the JSON into typed structs you define. That's a meaningfully lighter integration than clang-sys: no header/version-matching, no dlopen path-hunting — just "is `clang`/`clang++` on PATH." Still requires a real Clang install, but it's a strictly easier optional-dependency shape than libclang FFI.

**Compilation database: real degradation, not binary failure.** clangd's own docs and issues confirm: without `compile_commands.json` (or the simpler per-directory `compile_flags.txt`), it falls back to a generic command (default flags like `-std=c++20`) and drops into what its own docs call a degraded/basic-syntax-checking mode — no cross-compilation support, and a malformed fallback command yields diagnostics pinned to line 1 with most other features unavailable (clangd/clangd#784, clangd/vscode-clangd#547, clangd.llvm.org/design/compile-commands).

But there's a genuine, underappreciated Structural-tier win independent of full compile-command fidelity: **`-frecovery-ast`** (RecoveryExpr) has been on by default for C++ since Clang 11 (2020, LLVM D76696/D86602) — it preserves AST nodes across semantic errors (unresolved identifiers, overload failures, missing members) specifically because clangd needed navigation to keep working on broken code. This is Clang's own team already solving the "tolerate WIP/broken code" problem at the semantic layer — something tree-sitter structurally cannot do since it has no semantic layer at all. The real limit: RecoveryExpr only helps once a file is *found and parsed* — a missing `#include` is a preprocessor-level fatal "file not found" error with no equivalent recovery flag (clangd/clangd#695 and others confirm this is a constant real complaint). So the win is bounded: robust recovery over semantic gaps, no recovery over missing project headers. For header-heavy real-world C++ without real include paths, you're back near tree-sitter's ceiling; for self-contained or system-header-only files, Clang clears Heuristic easily.

**Pure-Rust C: `lang-c` (vickenty) is real but thin.** Crates.io shows a real gap worth flagging: last *published* 2023-09-04 (v0.15.1) but GitHub last *pushed* 2025-10-29 — two years of merged-but-unreleased work, a real single-maintainer bus-factor signal. C-only (no C++), claims "almost full C11" (not C17/C23). It's built on `rust-peg`, and rust-peg has no built-in error-recovery machinery — it's an open, unshipped feature discussion (kevinmehall/rust-peg#276) requiring hand-written skip-until recovery rules in the grammar, with no evidence lang-c's grammar does this. That's the same fail-fast risk that already ruled out `syn` for Rust. I found no other credible pure-Rust C parser on crates.io.

**C++'s ambiguity is real, documented, and structurally unsolvable except by real semantic analysis.** tree-sitter-cpp#74 (confirmed, still open) is exactly the `a * b;` expression-vs-pointer-declaration case: disambiguation requires knowing whether `a` names a type, which requires a live symbol table during parsing — not more lookahead, not better heuristics. Clang/GCC solve it by doing real Sema inline with parsing. Any "quick alternative" pure-Rust C++ parser hits the identical wall tree-sitter-cpp already hit; there is no known partial/heuristic escape from this specific class of ambiguity — only a real compiler frontend or an admittedly-approximate parse.

## Recommendation

- **C++**: Add an optional `libclang`-gated analyzer, feature-flagged and runtime-detected (prefer clang-sys's runtime/dlopen loading mode, or dtolnay's `clang-ast` subprocess approach for less integration friction), falling back automatically to the existing tree-sitter-cpp Heuristic tier when Clang isn't found. Cap it at Structural (not Exact) even with libclang unless a real compile database is present — RecoveryExpr buys real resilience to broken/WIP code but not to missing headers.
- **C**: Don't build a bespoke pure-Rust native analyzer around `lang-c` — its error-recovery gap mirrors the exact reason `syn` was rejected for Rust, and its release cadence is a real risk. Ride C along on the same optional libclang tier as C++ (C has none of C++'s context-sensitive ambiguity, so the same Clang integration gets C much closer to Exact for near-zero incremental engineering cost versus a second bespoke parser).
