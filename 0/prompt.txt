  - dependents: `"[results capped at 200; {tot_dep} dependents, {tot_imp} imports total]"` (`01-core-architecture.md:2332`, restated at `03-multi-language-platform.md:1174`)
  This is a direct instance of "we invented our own version of X" three separate times for the same underlying concern.
- **`05-research-and-decisions.md:24`** — Proposes extending `MonoklError` with a new `TraversalCapExceeded{visited, cap}` variant and a `TraversalReport{sites, truncated}` wrapper "rather than silently truncating a bare `Vec`," and explicitly notes *"the same bounded-BFS pattern generalizes to any of this spec's existing traversals... that don't yet have explicit cap enforcement at every site"* — i.e., monokl's own research log recognizes the cap/truncate pattern needs to be applied consistently but has no shared primitive to reach for, so it's reinventing it per traversal.
- **`07-edge-cases-and-failure-modes.md:23`** (cross-cutting pattern) — *"Resource limits are opt-out by construction. - **`07-edge-cases-and-failure-modes.md:129`** — *"The 50MB `io_safety` cap and the 2MB search token/byte budget coexist with no explained relationship — a 49MB file passes the safety gate, gets fully parsed, then has virtually all output discarded by the budget."* Two independently invented size-cap systems (`io_safety.rs`'s read-size cap vs. `budget.rs`'s token/byte cap) that don't compose — a symptom of not having one shared budget abstraction spanning read-time and output-time limits.
- **`06-daemon-architecture.md:163`** — The `PrecisionLedger` design deliberately keeps a compact `provenance` tag on every result by default, with full reasoning available only on demand via `explain` ("Default output stays terse; depth is opt-in.") — a progressive-disclosure output pattern invented ad hoc for this one subsystem rather than drawn from a shared primitive.

### 4. Resilience / retry-shaped logic

- **`01-core-architecture.md:3129`** — The LSP architecture description includes a genuine hand-rolled circuit breaker: *"`LspSession`... circuit breaker — 3 crashes in 60s → 'tripped', 500ms backoff."* This is real retry/backoff-shaped logic and a strong candidate for a shared michi-resilience primitive rather than a bespoke per-subsystem implementation.
- **`06-daemon-architecture.md`** §9 "Known gaps" (lines 242-250) plus the corresponding edge-cases findings are the richest resilience-gap cluster:
  - **`07-edge-cases-and-failure-modes.md:163`** — *"`Session(Owned)` resources have no orphan-detection or crash-recovery story, and no concurrent-ownership arbitration."*
  - **`07-edge-cases-and-failure-modes.md:164`** — *"`PrecisionUpgrader::upgrade()` failing mid-session has no defined degrade-back-to-baseline contract... No fallback-to-cached-baseline, no re-establishment story, no circuit-breaker against crash-looping."* This explicitly names the missing piece as a circuit breaker.
  - **`07-edge-cases-and-failure-modes.md:165`** — Kotlin/Scala's JVM-subprocess tier has no fallback-when-absent story, unlike the parallel C/C++ Clang-absent fallback — inconsistent degrade-policy across backends, i.e., no single shared "how do we fail over" primitive being reused.
- **`06-daemon-architecture.md:184`** (§6 rule 4) — *"When only generic LSP is available and no sentinel exists, cap at `Structural`... and emit a monokl `Diagnostic` explaining the downgrade rather than guessing"* — a degrade-and-explain pattern, resilience-adjacent, hand-specified per backend rather than via a shared transient-vs-permanent-failure primitive.
- **`07-edge-cases-and-failure-modes.md:34, 36-37`** — Cache-layer resilience gaps built entirely bespoke: no panic/stack-overflow guard around the parser in the main pipeline (unlike the napi boundary, which does wrap with `catch_unwind`, `01-core-architecture.md:2900-2932`); concurrent disk-cache writes race last-writer-wins; a genuinely corrupted `cache.json` hard-fails instead of self-healing (only the "stale version" case self-heals). The `03-multi-language-platform.md:998-1022` `fs2` advisory-lock fix (`with_cache_lock`) is monokl's own hand-rolled cross-process coordination primitive addressing part of this — another instance of building infra-level resilience machinery locally rather than drawing on a shared crate.

### 5. Other agent-ergonomics concerns

- **JSON key casing inconsistency** — `01-core-architecture.md:2525, 2646-2665`: `count_tokens` result uses snake_case (`total_tokens`, `tokens`, `path`) while every other command's output is camelCase (confirmed via the Section 24 snapshot dump, e.g. `search_top_level_keys` includes `totalTokens`/`truncationMarker`). A shared serialization convention would prevent this by construction.
- **Field-alias mapping hand-written per command** — `03-multi-language-platform.md:1658-1690` (`search_projection_fields`): `"snippet" =&gt; "code"`, `"score" =&gt; "finalScore"` is a bespoke, unenforced alias table; a shared projection/alias primitive (declarative rather than a per-command `match`) would generalize this instead of requiring a new hand-written function per new command (`inspect_projection_fields` at line 1692 duplicates the same shape for a different field set).
- **Hint/next-step text embedded as raw strings, not structured fields** — the search truncation marker (`01-core-architecture.md:1274`) tells the agent what to do next ("refine with +term or -term") entirely inside a free-text `Option&lt;String&gt;` rather than a structured "suggestion" type; likewise `dependents`' tsconfig-missing warning is a `Warning`-kind `Diagnostic` whose only machine-readable content is a message string containing the literal text `"tsconfig.json"` (`01-core-architecture.md:2332`). This is the "what to do next" agent-ergonomics concern being solved with ad hoc prose instead of a structured hint type.
- **Truncation/diagnostic/output-format design decisions have had zero cross-referencing against a shared library anywhere in the "decision log" doc** — worth restating as the top-line finding: `05-research-and-decisions.md` extensively researches and either adopts or rejects prior art for ranking, resolution, parsing, and eval methodology (SCIP, stack-graphs, ast-grep, difftastic, CHA/RTA/k-CFA, embedding rerank, etc.) but at no point asks whether monokl's own output/truncation/error/diagnostic machinery (Sections 1, 3, 4, 5 above) should be delegated to the sibling `michi` crate instead of being independently designed and re-derived per command. Given the project's own `CLAUDE.md` states monokl is supposed to depend on michi for exactly this ("agent-facing output rendering... structured errors, hints... rather than reinventing it"), this is a real gap in the spec's own research discipline, not just an implementation-detail oversight.
