<result># Research Findings: ra_ap_syntax vs syn, Salsa, and Rust Tokenization

## A. Bounding `ra_ap_syntax` parse-only throughput

No published number exists — confirmed harder. Checked directly: rust-analyzer's `crates/syntax` has no `benches/` directory at all ([GitHub API listing](https://github.com/rust-lang/rust-analyzer/tree/master/crates/syntax) — only `Cargo.toml`, `fuzz/`, `rust.ungram`, `src/`, `test_data/`). The historic ["Parsing seems slow" issue #1643](https://github.com/rust-lang/rust-analyzer/issues/1643) diagnosed redundant `Parser::nth` lookahead and Arc-drop overhead but published no throughput figure. The 2024 [issue #17491 "A Plan for Making Rust Analyzer Faster"](https://github.com/rust-lang/rust-analyzer/issues/17491) contains the "twice as slow as syntree" claim verbatim (contributor davidbarsky, benchmarking *tree construction only*, explicitly caveated as unfair since rowan's structural sharing serves incremental editing that syntree doesn't do) plus the "lack of mechanical sympathy" critique (heap-allocated Arcs, overused hashing, underused indexing, no identifier interning). `rowan`'s own repo/docs publish no benchmarks.

Two adjacent anchors help bound it. [tree-sitter-rust](https://github.com/tree-sitter/tree-sitter/discussions/3429) — also a lossless, error-recovering CST parser — is reported ~3x slower than rustc's hand-written parser. [`syn`](https://fasterthanli.me/articles/the-virtue-of-unsynn), an AST-only parser assuming valid input, is anecdotally reported parsing ~11,000 lines in ~100ms in a warm-build context — not a rigorous MB/s figure, but a real data point (order of ~100K+ lines/sec). No apples-to-apples benchmark of `ra_ap_syntax`/`rowan` against `syn` or tree-sitter-rust exists anywhere I could find.

**Best-bounded estimate:** lossless CST construction (trivia preservation, green/red tree, structural sharing) is inherently more work per token than `syn`'s AST-only parse of already-valid tokens. Combined with the 2x rowan-vs-syntree gap and tree-sitter's ~3x-vs-rustc gap, expect `ra_ap_syntax` to land in the same broad order of magnitude as tree-sitter-rust — plausibly 3–10x slower than `syn` per byte — likely low tens of MB/s on modern hardware rather than the ~100+ MB/s a bare AST parser could hit. For per-invocation CLI use over typical repo sizes (thousands of files, not gigabytes), this is probably still acceptable latency, but it is not free.

## B. `syn` as the structural-tier alternative

`syn` gives up exactly what the spec's questions predicted: no lossless trivia (comments/whitespace aren't first-class tree nodes the way ra_ap_syntax's CST preserves them for verbatim block-text reproduction), and no incremental reparse (moot here since monokl's Rust tier is cold per-invocation anyway). The sharper, *practical* concern is error recovery. `syn::File::parse` fails fast: [`syn::parse::Error`](https://docs.rs/syn/latest/syn/parse/struct.Error.html) documents returning `Err` at the first bad token, with the recommended pattern being to emit `compile_error!` and stop — there is no "give me what parsed and mark the rest broken" mode. `ra_ap_syntax` is IDE-designed specifically to always produce a tree, tagging error nodes rather than aborting. For monokl, which searches real working trees — WIP branches, merge-conflict markers, mid-edit files — a single syntax error anywhere in a `.rs` file would make `syn` yield zero symbols for that entire file, while `ra_ap_syntax` keeps extracting symbols around the error. That is a real regression, not a theoretical one.

## C. Salsa as monokl's own cache, independent of `ra_ap_hir`

Salsa is a generic, IR-agnostic memoized-query engine, not coupled to rust-analyzer's data model. Two concrete precedents of standalone use: Astral's **ty** (formerly red-knot) Python type checker built its own Salsa-based incremental system from scratch, independent of rust-analyzer's queries ([talkpython.fm](https://talkpython.fm/episodes/show/506/ty-astrals-new-type-checker-formerly-red-knot), [DeepWiki](https://deepwiki.com/astral-sh/ruff/6-red-knot-type-checker)); and **Biome**, a JS/TS linter/formatter toolchain in a domain adjacent to monokl's, uses Salsa in its workspace/analyzer layer (evidenced by a recent [salsa-setter deadlock fix](https://github.com/biomejs/biome/commit/6450276764ee4794a0fcb46c139f95b68d892427)). Monokl could define its own queries (symbols-for-file, postings-for-term) memoized on content hash, without touching `cargo metadata`/crate-graph machinery — a materially lighter proposition than embedding `ra_ap_hir`. Caveat: Salsa's API has undergone significant breaking rewrites; pin a version deliberately.

## D. Tokenizer, grounded in `tokens.rs` (monokl-spec.md:866-937)

Traced each construct against the actual code. `vec!`/`println!` → `!` is a pure separator, base identifier survives as "vec"/"println" (fine). Turbofish `::&lt;Vec&lt;u8&gt;&gt;` → `::`/`&lt;`/`&gt;` are separators, inner identifiers tokenize normally, single-letter generics (`T`) correctly dropped by the len≥2 filter. `#[derive(Debug, Clone)]` → tokens "derive", "debug", "clone" — meaningfully indexed, contrary to worry. Confirmed gap: `'a` is dropped as noise (apostrophe separates, "a" is len-1). Longer lifetimes (`'ctx`, `'static`) survive but collide indistinguishably with plain identifiers — minor precision loss. A real, cheap-to-fix gap: `STOP_WORDS` includes `mod`/`impl`/`pub`/`type` etc. but omits `crate`, `self`, `super`, `dyn`, `async`, `await`, `unsafe` — these will appear as high-frequency near-universal tokens across any Rust corpus (BM25's IDF partially compensates, but it's free precision left on the table). Edge case: raw identifiers (`r#type`) vanish entirely since the escaped keyword is itself a stopword.

## Recommendation

Keep `ra_ap_syntax` for the structural tier. Its error recovery on malformed/in-progress code is a load-bearing feature for a search tool scanning real working trees, not a nice-to-have — `syn`'s fail-fast model would silently blank out symbol extraction for any file with a syntax error, which is worse than the unquantified throughput cost of the CST. Investigate Salsa separately and independently of the `ra_ap_hir` question — it has real standalone precedent (ty, Biome) and would give monokl warm-daemon-style incremental recomputation for its own queries without a crate-graph load. For the tokenizer, add `crate`, `self`, `super`, `dyn`, `async`, `await`, `unsafe` to `STOP_WORDS` as a low-cost precision improvement; no other change is warranted.</result>
