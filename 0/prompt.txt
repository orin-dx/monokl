## Recommendation: adopt a generic tree-sitter fallback tier, but scope it tightly and reset expectations that per-language config stays "thin"

### Grammar maturity findings (per candidate)

### Precedent for the architecture pattern

- **universal-ctags** already runs a two-tier model structurally similar to what you're considering: hand-written full parsers for complex languages, plus a genuinely generic, user-extensible regex-based "optlib" mechanism for everything else. optlib is real precedent that a thin/generic tier can work — but it's correspondingly low-precision (pattern/tag matching, no real tree), i.e. it validates Heuristic-only as the honest ceiling for a truly thin tier.
- **Sourcegraph** ships almost exactly your proposed shape at the product level: fast, always-available "search-based" nav (generically powered by ctags + tree-sitter) as a fallback alongside precise SCIP/LSIF nav for repos with real indexers. Credible evidence this two-tier shape is a legitimate, shipped product pattern, not a compromise nobody actually uses.
- **GitHub Linguist** is not real precedent here — it's heuristic pattern-matching + statistical classification for language ID, not AST-based analysis, so it doesn't validate a code-intelligence fallback tier specifically.
- **The strongest and most important finding**: codegraph — the tool this whole idea came from — does **not** actually keep its per-language config thin in practice. Its own architecture docs and issue tracker show real, substantial special-casing per language: Kotlin needs custom nested-property-declaration visiting, Java needs Lombok member synthesis (the *exact* problem monokl already solved bespoke), C# needs generic-unwrapping/nullable-stripping, C++ needs smart-pointer unwrapping, COBOL needs a fixed-to-free preprocessing pass before parsing even starts. Codegraph's maintainers describe this as ongoing, expected growth. This directly contradicts the "thin config" premise the idea was originally sold on — it's aspirational, not descriptive of what production quality actually requires.

### Architectural cost to monokl

Expect the same erosion codegraph experienced: any fallback-tier language that gets real usage will draw pressure for special-casing, and that pressure won't stop on its own — it has to be actively capped by policy (Heuristic-only ceiling, no `InspectEntry` classifier, no resolution beyond textual/structural reference-finding). The minimal-viable shape, following both ast-grep's precedent (no cross-language node-kind normalization) and codegraph's own `LanguageExtractor` interface shape (per-language string-keyed node-type buckets: functionTypes/classTypes/etc.), is a single generic analyzer keyed by extension, internally dispatching to a small per-language config table. That fits `AnalyzerRegistry`'s existing one-impl-per-language dispatch as one additional impl owning N languages — no dispatch restructuring needed. The one real twist: `CapabilityPrecision` needs to be reported per-language-instance inside that one analyzer, not per-analyzer-impl, since C's ceiling (Heuristic/Structural) genuinely differs from C++'s (Heuristic only, given the ambiguity) and Kotlin's (Heuristic only, given the 61% ceiling) — existing analyzers don't need this since each is already one language.

### Launch set (prioritized by real usage data)

2. **C++** — TIOBE #3, real gap, but declare Heuristic-only at launch (not Structural) given the unresolved ambiguity; expect it to generate the most special-case pressure.
3. **Bash** — cheap, low-risk, real demand.
4. **C#** — grammar-quality objection doesn't apply to fallback-tier scope; include.

### Graduation threshold (fallback → bespoke Go/Java-style investment)

Two-part test, not usage rank alone: (a) sustained usage in the current Go/Java tier (top ~10-12 TIOBE/Octoverse) **and** (b) documented evidence of a structural-precision ceiling analogous to Java's Lombok problem — i.e., idioms common enough in real code that Heuristic/Structural-only output silently breaks call-chain/symbol resolution for a large fraction of real codebases. **C++ already meets both today** — it's the strongest near-term graduation candidate, and worth revisiting for a native-parser bespoke investment (mirroring the OXC/gosyn/ra_ap_syntax pattern) rather than assuming tree-sitter fallback is permanently sufficient for it.
