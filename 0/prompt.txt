I've read the trails overview and the gates page.

What trails are:
- A trail replaces the pull request in Entire's model. It holds the intent (title, description, type, priority), the linked branches (changes), the agent sessions, and the review evidence.
- A change is one linked branch in one repo. Each change merges separately. The trail has open and closed status, and "Planning" is the phase before any branch is linked.
- For GitHub mirrors, CI and merging still run through a linked PR. Entire review and GitHub review are separate and both must pass.

Gates: these are per-repo merge requirements, set under Settings → Gates:
- Up to Date: the branch is current with its base.
- Human Review: a minimum number of approvals, and whether a push resets them.
- Agent Review: unresolved findings from the trail-review runner, blocking at a severity threshold you choose.
- Checks: GitHub CI.

What this means for your scoping question:
- The recommended workflow starts by capturing the intent: problem, outcome, acceptance criteria. So a trail should be feature-sized with a done state, which confirms you were right about "v1 hardening".

  ## Implications for monokl (prioritized)
  
  1. **Return code, not only names.** Emit a ranked file:line hit with 1 to 3 lines of matched context, grouped by symbol. The evidence is Cognition's line-range F1 reward, Anthropic's "high-signal fields" guidance, and the LSP paper's finding that "text-enriched" results recover most of the gap. Our eval's 6x token loss to ripgrep likely comes from agents having to re-read after a name-only result. Hard evidence on snippet versus no-snippet shape is thin, so test it in our own eval.
  2. **Add a text fallback over all content.** Index or scan comments, string literals, calls, routes, config and tests, not just top-level declarations. The LSP paper shows renames and literals need text matching, and Cursor and Cognition both keep grep as a core tool. Implement via `ignore` plus `grep-searcher` for a residual lexical pass, with no persistent index (consistent with PRINCIPLES). Treat declaration BM25 as a boosting signal, not the sole index.
  3. **Never return silent empties.** Return a structured message with the count scanned, which terms matched zero, near-miss identifiers and a next-step hint. Evidence: Anthropic's actionable-error guidance and Agent Retrieval Bench's finding that abstention is poorly calibrated, which argues for hints over silence.
  4. **Rank members above containers (or collapse them).** Score at member level and attach the parent as context. A class should not outrank the method that matches. This rests on our own eval plus Cognition's precision-favoring F-beta. No source tests it directly.
  5. **Expose a concise/detailed mode and an explicit budget.** Default concise, with counts like `items_returned`/`items_total` and a truncation note that steers toward narrower queries (Anthropic, including the 25K cap). Keep it well below that cap.
  6. **Make compact JSON or a plain table the default, with TOON optional.** TOON's own README shows its gains are 5 to 10% in flat cases and negative against compact JSON on nested ones. Agent-facing hits with context are not uniform tables. Benchmark on our eval before committing.
  7. **Tokenize identifiers into subtokens plus the whole identifier**, with acronym handling, and index path tokens. Evidence is weak (crate practice only). Verify it ourselves with an ablation.
  8. **Provide a RepoMap-style summary mode** (outline of files and exported symbols within a token budget). It was the best performer at an 8K budget in Agent Retrieval Bench, and it plays to our declaration-only strength.
  9. **Keep OXC.** The TS 7 native port removes the JS compiler API but not syntactic parsing. Avoid depending on type information. If type-aware features are ever needed, the oxlint/tsgolint pattern (spawn a Go binary) is the precedent.
  10. **Defer embeddings.** Cursor's +12.5% is the strongest pro-embedding evidence, but it comes from a vendor-trained model on a vendor benchmark. Agent Retrieval Bench shows embeddings winning MRR. This can revisit PRINCIPLES.md later, but it is not the first fix.
  
  ## Things that contradict our current direction
  
  - **"No code in output."** Every agent-design source returns locations plus context; our eval confirms the cost.
  - **"Index only top-level declarations."** The LSP paper shows grep wins where text in strings, comments or calls matters, and that agents default to grep.
  - **"No persistent index / no embeddings" as an unquestioned non-goal.** The 2608.01507 and Cursor results favor an index for question-answering workloads. The mixed grep-vs-vector evidence cuts both ways.
  - **TOON as the output format.** Its own benchmark shows small, within-noise gains and weak fit for non-tabular data.
  - **Planned dependents and symbols commands.** The LSP paper suggests semantic reference tools often cost more tokens than grep and agents under-use them. Prove value in the eval before building.

  1. **Matched lines with no block are dropped with no accounting (high; verified by running).**
     - `retrieve_blocks` (pipeline/mod.rs, the `inside` filter) keeps only hits that fall inside a top-level statement block. `statement_kind` (analysis/ts/parse.rs ~L400) returns None for namespaces, `declare module`, `declare global`, `import x = require`, `export =` and expression statements.
     - Run: `monokl search modNeedle` (inside `declare module 'foo' {}`), `globalNeedle` (`declare global`), `eqNeedle` (`export =`), `cjsNeedle` (`module.exports =`) and `topAwaitNeedle` each print `search: []` with exit 0.

     - Declarations are dropped too, not only the statements the earlier audit listed.
     - Nothing counts hits against blocks. `files_total` counts the file as matched, yet no diagnostic says "N matching lines belong to no block".
     - Fix: add a conservation check (hits to blocks). Unclaimed hits become fallback line-range blocks, or at least a rendered "N lines unattributed" count.
  
  2. **One non-UTF-8 byte anywhere in a file loses the whole file (high; verified by running).**
     - Text search only requires the matching line to be UTF-8, but `read_source` (pipeline/mod.rs) uses `read_to_string`.
     - Run: `export function latinFn(){}` plus a `// caf\xe9` comment line gives `search: []`, exit 0. ripgrep finds it.
     - UTF-16 files (NULs) are classified Binary and skipped with no diagnostic (verified: `utfsixteen` gives `[]`).
     - Fix: read bytes and decode lossily, since line numbers are byte-based and the `\n` bytes are unchanged. Count the BOM-less UTF-16 and binary skips.
  
  3. **Candidates are chosen by substring match, but scored by exact-token equality (high; verified by running).**
     - Text search uses `regex::escape(term)` with no word boundary. BM25 compares lowercase sub-word tokens exactly (bm25.rs, tokens.rs).
     - Run: `search auth` over `authenticateUser` (a.ts) and `authToken` (b.ts) ranks b.ts first. The a.ts block scores 1, which is only the coverage boost.
     - Any prefix, plural or stem query (`auth`, `parse` vs `parsing`) scores 0 BM25. Ranking then collapses to coverage and the file-path tie-break, so it is effectively alphabetical.
     - Short terms like `id` also match `width` and `valid`, and every such line becomes a candidate block (see 6).
     - Fix: score with the same substring semantics, for example by adding tokens that have the query token as a prefix. Or restrict candidates to token matches by default, with substring behind a flag.
  
  4. **`coverage_boost` is relative to the file, not to the block (medium; from reading only).**
     - rank/boost.rs divides the matched lines inside the block by all matched lines in the file. This is the 0-to-1 additive term in `final_score` (rank/mod.rs).
     - A file with one weak hit gives its block +1.0. A dense block in a file with 30 hits across 3 blocks gets +0.33.
     - It is not comparable across files and is on the same scale as BM25, so a file with a single hit outranks a dense match.
     - Fix: use the block's matched lines divided by its line count, or drop the term.
  
  5. **Fixed tokenizer startup cost of about 110 ms on every search that has a hit (medium; verified by running).**
     - Run: a one-hit search takes 0.117 s total. A no-match search takes 0.006 s.
     - The cost is `tiktoken_rs::o200k_base_singleton()` loading its vocabulary in `count_tokens` (budget.rs).
     - Agents call this tool many times per task, and ripgrep returns in about 5 ms.
     - Fix: estimate tokens by byte length divided by 4 until a block is near the cap, or lazy-load only when close to `max_tokens`. Keep exact counting behind a flag.
  
  6. **Performance architecture: one sequential pipeline with whole-corpus memory and no deadline (high; code read, timing partly run).**
     - Reads, parses and CPU work:
       - The walk and grep are sequential: `WalkBuilder::build()`, not `build_parallel`, and no rayon despite the workspace dependency and the docs.
       - `passthru(true)` forces every line of every file through the sink, which defeats the searcher's literal and `memchr` skipping.
       - For CRLF files each line is copied and re-searched with a second `Searcher` (`LineCollector::text_matches`).
       - Every file the walk meets is read in full by text search, not just analyzable ones. Large `.json`, `.map` and `.log` files are scanned to the first NUL or EOF.
       - A `-term` query walks and greps the whole tree again (`max_files: usize::MAX`), then re-reads and parses the survivors a third time.
       - Each surviving file is read a second time with `read_to_string`, then parsed.
       - `AnalysisProfile::Full` computes symbols, exports, dependencies and a blake3 digest. It also does a full extra JSX AST walk and a `LineIndex` over all bytes. Search uses none of that except the blocks.
       - All top-level statements get `code.to_owned()`, and then `block.clone()` copies again in `retrieve_blocks`, before the check on whether any hit lands inside the block.
     - Memory:
       - It holds every matching line text (`BTreeMap<Utf8PathBuf, Vec<LineHit>>`), every candidate block's code, and a `Vec<String>` of tokens per block, all before ranking and budgeting. One heap `String` per token.
       - Memory is proportional to the total size of all blocks containing a hit. The 50-result cap is applied last.
     - Scaling and cancellation:
       - There is no deadline, cancellation or progress output. The caller cannot tell a slow search from a hung one.
       - The `inside` filter is O(blocks x hits) per file.
     - Measured:
       - Corpus: 3,000 files, 47 MB across `src/` and a CRLF copy, 120,000 functions in total.
       - `handler17_3` (11 results): 0.70 s on the LF tree. `rg -c` takes 0.11 s on the same tree.

     - ripgrep difference: parallel walk, mmap or buffered literal prefilter, bounded memory, streaming output.

       - Do the grep as a prefilter in a rayon walk.
       - Apply the cap on files before parsing.
       - Parse and extract only blocks that contain a hit.
       - Pass the already-read bytes through instead of re-reading.
       - Add an overall deadline that yields a partial-result diagnostic.

If the file changes between the two (an editor save, a build writing generated files), blocks and hits no longer line up. Nothing compares them: `LineHit.text` is stored but never checked against the block, and the digest is computed but never compared.

  ### Design (all in `crates/monokl/src/analysis/ts/parse.rs`)
  - **Own thread per file:** each file's parse and extraction run on a scoped thread with 8 MiB plus 4 KiB of stack per source byte (12 KiB in unoptimized builds).
  - **Why that is a proof:** every recursion level consumes at least one byte of source, and the stack is more than twice the worst measured cost per byte. No input under the limit can overflow it.
  - **Length limit:** files that would need more than 1 GiB are degraded without parsing. That is anything over 254 KiB in release builds, 85 KiB in unoptimized ones.
  - **Failures:** a panic, or a thread that cannot start, also gives the degraded result. The result goes out through the existing `had_parse_errors` → `Degraded` diagnostic path.
  - **Scope kept small:** no public API change, no new dependencies.
  - **Bracket scan:** kept as an early exit for absurd nesting. It now skips regex literals and ends quoted strings at the end of the line.
  - **Rejected:** a smarter scan as the only bound (a crafted file can always desynchronise it), a fixed big stack with the scan as the bound, a child process per file, `stacker`, and a stack proportional to length with no limit.

<pasted_content id="bbdd">
Their notes confirm the same failure classes we hit, and I checked the one claim that affects us. In the plugins repo, courier's changeset reference does group release notes under ### Breaking Changes, ### New Features and ### Bug Fixes. Callisto renders a flat bullet list, and the plugins mention Callisto only in a changelog line. So courier:changeset output can't go into our .changeset/ as is. Our workers wrote the changesets by hand, in the flat style, so we didn't hit it. Don't use courier:changeset for caliper until there is a Callisto-shaped mode. I have not checked how entries are ordered, which they report is by filename.

What matches our findings. Their list is nearly ours, which is reassuring but not independent evidence. It also points at the same root cause: every brief said "fix this finding" and every check said "tests pass", so nothing measured that the class was gone. Shared items:
- Siblings missed, silent failure, copy drift, premise errors in claims, and release-path failures.
- Docs describing intent, and shape-only tests.
- Reviews seeing only the diff, so old code is never reviewed.
- "Green is easy to fake."

New ideas worth taking, with how they apply here.
1. Conservation test. Whenever a step filters or skips input, the output accounts for every input, either as a result or as a counted diagnostic. This is the strongest guard for our biggest sweep class, components dropped without a word. A test would assert that every candidate declaration or file either yields a component or a skip entry with a reason. It's generic and cheap.
2. Hints checked against reality. A contract test that every hint or recovery text names a real command or flag. Ours blamed the wrong cause (for example, "check the package is installed" when typescript was missing).
3. Release rehearsal on every PR that touches the release workflow. A read-only dry run in CI. For us it must include a real Linux build step, because the napi suffix failure was in the build, not in planning.
4. Success measure with a named baseline. For caliper this is already written down: accuracy against the TypeScript checker with wrong near zero, and the first load of Storybook. But the weekly job only reports them. Nothing gates a resolver change on them. The oracle on antd and shadcn is the gate nobody has run.
5. A changelog render before merge. Actually rendering the changelog caught wrong doc lines for them. We validated changesets with callisto status --check --strict but never rendered the entries. I haven't checked their order for caliper.
6. An invariants map. One file listing each repo invariant and what enforces it: a lint, a test, a CI grep, or "convention only". Ours would show where we rely on convention.
7. Claims cite a command. Their sweep verifier mislabelled real findings, and a "template unchanged" claim hid a broken release. Ours: inverted verdict labels, overstated severities, and my own "0 open findings".
8. Over-engineering filter. "Fix what's valid" is right, and they flag their own borderline additions.

What's specific to caliper. These stay in this repo, as ADR guardrails, architecture-model invariants, AGENTS.md, and CI checks:
- The goal: type correctness for Storybook over RDT parity, with a first load that is imperceptible.
- The gate command and what a clean checkout means in this monorepo.
- Contract sites: the Storybook peer range, pins, the release group, the schema-version copies, the cache version and its golden file.
- Resolver order-independence, the ground-truth harness, and the corpora.
- Platform floors and the Callisto release path.

What goes in the plugins (each stated as a class, with the swap test: would it hold for a Go CLI or a Python library?):
