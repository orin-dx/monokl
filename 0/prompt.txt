## 7. Literature grounding: CHA/RTA/k-CFA and points-to analysis vs. `CapabilityPrecision`

Call-graph and points-to analysis is a mature subfield with a clean precision/cost ladder that
maps onto `CapabilityPrecision` (`Unsupported < Heuristic < Structural < Exact`) better than
expected, with one real gap the literature exposes.

**Class Hierarchy Analysis (CHA)** — Dean, Grove, Chambers, "Optimization of Object-Oriented
Programs Using Static Class Hierarchy Analysis," ECOOP 1995, pp. 77-101. CHA resolves a virtual
call from the declared class/interface hierarchy alone: any subtype of the static receiver type is
a possible target, full stop — no dataflow, no reachability, no instantiation check. Fast, purely
syntactic, known-unsound (ignores reflection, dynamic loading, generics-driven dispatch). This is
`TraitImplIndex`'s (§2) shape exactly: it indexes every `impl Trait for Type` from the AST with no
check on whether `Type` is ever constructed — a declared-hierarchy fact, not a program-behavior
fact. `Structural` is a correct label for this.

**Rapid Type Analysis (RTA)** — Bacon & Sweeney, "Fast Static Analysis of C++ Virtual Function
Calls," OOPSLA 1996, pp. 324-341. RTA refines CHA with one extra static pass: track which classes
are actually instantiated (`new`) anywhere in the reachable program and prune CHA's target set to
those. On their benchmarks (7 C++ programs, 5-20 KLOC) this resolved 71% of virtual calls
statically, vs. CHA's much larger over-approximation. Critically, RTA is still single-pass,
non-iterative, and needs no aliasing or points-to information — it costs the same order as CHA,
not the order of a real type checker. That means RTA is not a stand-in for `Exact`; it is a
finer-grained rung *inside* what monokl currently collapses into one `Structural` tier. Concretely:
CHA-shaped = "declared hierarchy says `Type` could implement `Trait`"; RTA-shaped = "...and `Type`
is actually constructed somewhere in this corpus." An RTA-style filter over `TraitImplIndex` —
cross-referencing implementor types against observed struct-literal/constructor sites, already
information monokl's `SymbolIndex` pass collects — is a legitimate, still-`Structural`-cost
enhancement worth recording, not a new precision tier.

**k-CFA** — Shivers, "Control-Flow Analysis of Higher-Order Languages, or Taming Lambda," PhD
thesis, CMU-CS-91-145, May 1991 (formalizing the earlier "Control-Flow Analysis in Scheme," PLDI
1988, pp. 164-174). k-CFA answers a different question than CHA/RTA: not "which subtype could this
be" but "which closure could this call site invoke," by abstracting environments to
k-deep call-string contexts. It is EXPTIME-hard for any static k>0 — Van Horn & Mairson, "Deciding
kCFA is complete for EXPTIME," ICFP 2008, pp. 275-282 — and the blow-up is fundamental, not an
implementation artifact (companion result: Might, Smaragdakis, Van Horn, "Resolving and Exploiting
the k-CFA Paradox," PLDI 2010, showing even k=1 degenerates badly on OO-flavored code specifically
because class-based dispatch, monokl's actual target, isn't what k-CFA's context-sensitivity is
built to disambiguate). k-CFA is the wrong shape and the wrong cost class for monokl: it targets
first-class-closure flow in dynamically-typed/functional code, not "what implements this
interface" or "what does this import resolve to." Tellingly, even IDE-scale JS tooling built for
monokl's actual problem class explicitly avoids it — Feldthaus, Schäfer, Sridharan, Dolby, Tip,
"Efficient Construction of Approximate Call Graphs for JavaScript IDE Services," ICSE 2013, use a
cheaper field-based approximate analysis instead of full k-CFA specifically to hit interactive
latency. Verdict: k-CFA is correctly out of scope; no part of this spec should be revised toward it.

**Points-to analysis** — the two foundational styles: Andersen, "Program Analysis and
Specialization for the C Programming Language," PhD thesis, DIKU, University of Copenhagen, 1994
(inclusion-based/subset-constraint, more precise, worse complexity); Steensgaard, "Points-to
Analysis in Almost Linear Time," POPL 1996, pp. 32-41 (equality-based/union-find, "almost linear,"
less precise). Bravenboer & Smaragdakis, "Strictly Declarative Specification of Sophisticated
Points-to Analyses," OOPSLA 2009 (the Doop framework), show Andersen-style points-to specified in
Datalog scales across a dial of context-sensitivity (context-insensitive up to k-object-sensitive)
rather than being one fixed cost point — the literature's actual answer for what a non-`ra_ap_hir`
path toward `Exact` looks like, relevant to the open Salsa/persistent-daemon track (§4) as a second
candidate design, not just `ra_ap_hir`.

**Recent IDE-scale precedent.** PyCG (Salis, Sotiropoulos, Louridas, Spinellis, Mitropoulos, ICSE
2021, arXiv:2103.00587) — dependency-free static call-graph generation for Python — reports 99.2%
precision but only 69.9% recall, concrete quantified evidence that even careful assignment-based
static analysis without type inference has a real recall ceiling for a dynamic language, directly
backing this doc's own admission (§04-analysis-fidelity.md, problem 5) that Python forward-reference
resolution without pyright is `Heuristic`, not `Structural`. SootUp (Karakaya, Schott, Klauke,
Bodden et al., TACAS 2024) modernizes Soot's engineering (lazy class loading, fail-early
validation) but not its cost model — full points-to/call-graph construction there is still a
batch, whole-classpath operation, reinforcing rather than challenging monokl's daemon/non-daemon
split. No CodeQL/Semmle paper describing an explicit graded-precision model comparable to
`CapabilityPrecision` was found — de Moor et al., "Keynote Address: .QL for Source Code Analysis,"
SCAM 2007, pp. 3-16, describes the Datalog query engine, and CodeQL's public Java/Kotlin call-graph
docs describe one virtual-dispatch-aware resolution strategy with no published notion of graded
confidence tiers. Worth stating plainly rather than implying false precedent.

**Verdict:** no new tier needed, and no change to k-CFA's exclusion. One concrete, low-cost
documentation fix: `Structural`'s definition in §11 should note it currently spans both a
CHA-shaped fact (declared-hierarchy membership) and would span an RTA-shaped fact
(hierarchy-membership-plus-instantiation) if the `TraitImplIndex` instantiation filter above is
ever built — both are real, distinct precision levels in the literature that this spec currently
collapses into one label. That collapse is defensible as shipped (same cost order, same
soundness caveats), but should be named rather than left implicit.
