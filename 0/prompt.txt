## 3. DKB Algorithm — concrete, but simpler than the terminology implies
Construction: two Tree-sitter passes over Java — Pass 1 registers class/interface/enum/record/annotation declarations as nodes; Pass 2 adds typed edges (`injects` from field/constructor-parameter type references, `extends`/`implements` via `child_by_field_name("superclass"/"interfaces")`), stored as a **NetworkX DiGraph** with edge attribute `relation`. Critically, per the actual source, **"bidirectional traversal" is a single 1-hop expansion**, not a depth-parameterized BFS: at query time it takes `graph.successors(node)` (what the class depends on) and `graph.predecessors(node)` (what depends on it) — no recursion or depth loop exists despite the paper's Algorithm-1 prose implying a depth variable *d*. "Interface-aware expansion" = if a successor edge has `relation=="implements"`, the code additionally fetches `predecessors()` of that interface node (other implementers/consumers wired to it) and merges them in — computed on-the-fly by walking the same graph twice, not a precomputed implementor index. For a Rust port: petgraph DiGraph, nodes = types, edges = enum{Injects,Extends,Implements} from tree-sitter-java queries on `field_declaration`/formal params/`superclass`/`super_interfaces`; at query time gather seed's direct successors+predecessors, then for any Implements successor, also gather that interface's predecessors, dedupe, emit.
