## difftastic research findings

**1. Core algorithm** — Confirmed from Wilfred Hughes's primary source ["Difftastic, the Fantastic Diff"](https://www.wilfred.me.uk/blog/2022/09/06/difftastic-the-fantastic-diff/): after parsing, difftastic converts each tree-sitter tree to a uniform s-expression (`List{open, children, close}` / `Atom{position, content, kind}`, in `src/parse/syntax.rs`). Diffing is framed as **shortest path on a DAG**: a vertex = `(left_position, right_position, parent-exit-stack)`; edges cost less for "unchanged" matches, more for novel/added/removed atoms; **Dijkstra's algorithm** finds the min-cost route = "most unchanged edges." This is fundamentally a **sequential positional alignment** (walking both flattened token streams in lockstep, tracking nested-list entry/exit), not a general tree-edit-distance over subtree identity.

Graph size is O(L·R) (quadratic in token counts) but vertex parent-stacks made it naively O(2^N) in nesting depth — fixed by lazily constructing vertices and capping to "at most two graph vertices per position pair." Biggest bottleneck is vertex construction itself (millions of vertices on large diffs). Mitigations: aggressive prefix/suffix trimming of unchanged regions, and a **fallback to plain line-diff when the graph would be too big**. A* was tried as an alternative router — "didn't see much improvement" over Dijkstra.

A follow-up optimization write-up, ["How do I boost difftastic by 4x"](https://blog.quarticcat.com/posts/optimize-difftastic/), shows the real-world perf work was almost entirely **shrinking the `Vertex` struct** (nested enums → bitmap → pointer-tagged pointer+counters, −8 bytes/vertex), pruning zero-weight-edge chains (15-25% search-space cut), reusing neighbor-vector allocations, and switching allocators (mimalloc→jemalloc, trading ~20% runtime for fewer pathological-case blowups) — net 4x speedup, 23% of original memory. Confirms the algorithm is Dijkstra over a huge lazily-built graph, and that its dominant cost is memory/allocation engineering, not asymptotic algorithm choice.

**2. Alignment / move detection — the key finding**: difftastic does **not** do tree-edit-distance-style arbitrary subtree relocation matching. [Issue #508 "Highlight moved, novel regions"](https://github.com/Wilfred/difftastic/issues/508), opened by Wilfred himself in 2023 and still open/unimplemented, explicitly proposes this as future work ("if a subtree is deeply novel on both sides but exists on both sides, it could be treated as a move"). Because the core graph only walks `(left_pos, right_pos)` pairs in order, a block moved far away in the file just shows as delete+add, not a detected move. The [manual's Tricky Cases page](https://difftastic.wilfred.me.uk/tricky_cases.html) documents related alignment weaknesses: depth-invariant node matching (`(x)` vs `[x]`), punctuation deprioritized in matching, "slider" misalignment on repetitive/flat structures, and explicit non-support for unordered-collection diffing (NP-hard in general, so intentionally skipped).

**3. Multi-language support**: per the ["Adding a Parser" manual](https://difftastic.wilfred.me.uk/adding_a_parser.html), each language needs: a tree-sitter grammar crate, an entry in `tree_sitter_parser.rs` with `atom_nodes` (node kinds that must be treated as leaves despite having children — misconfiguring shows spurious diffs), `delimiter_tokens` (paired delimiters — omitting causes `(`/`)` to be diffed independently and mismatched), and a highlight query; plus a `guess_language.rs` entry for file-extension/shebang detection. 44 languages supported; the process is described as genuinely lightweight, but `atom_nodes`/`delimiter_tokens` are real per-language tuning, not free.

## Takeaways for monokl's `diff` command

- **Difftastic's approach is likely overkill for monokl.** Its Dijkstra-on-a-huge-graph design solves *minimal, aesthetically-good, general-purpose text-level diffs* — optimized for human readability in a terminal, at real engineering cost (the entire 4x-speedup post is memory-layout surgery on a graph search). Monokl's actual need — "summarize semantically what changed" for an agent — doesn't require finding a globally-minimal edit script at all.
- **What's actually worth borrowing**: (a) converting each language's AST to one **uniform intermediate representation** (list/atom) so diff logic is language-agnostic — directly reusable given monokl already normalizes across OXC/tree-sitter/ra_ap_syntax; (b) per-language `atom_nodes`-equivalent config (which node kinds are "atomic" for diff purposes) and `delimiter_tokens`, since monokl will hit the exact same false-diff bugs without it.
- **Skip**: the Dijkstra/DAG shortest-path machinery and its vertex-memory optimization work — that's solving a harder, more general problem (minimal textual diff) than "what semantic entities (functions/classes/imports) changed," which monokl can likely answer with simple top-down tree matching (match named declarations by name+kind, recurse only into matched pairs, treat everything else as added/removed) — closer to a shallow tree-diff than a full edit-distance.
- **Move detection is explicitly unsolved even in difftastic** (issue #508 open since 2023) — don't expect to get "this function moved" for free from any off-the-shelf approach; if monokl wants that, it's a separate, tractable win: hash/fingerprint named top-level declarations (by normalized subtree content) and match by hash across the two trees before diffing, independent of position. That's cheap and gives monokl something difftastic still lacks.
- **Fallback-to-line-diff-when-too-big** is a pattern worth keeping regardless of algorithm choice — monokl's `diff` should have a size/complexity ceiling per file with a graceful degrade path, since even a from-scratch Rust structural differ can hit the same pathological-input problem difftastic did.
