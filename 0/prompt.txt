## Kotlin

**Compiler-as-library status:** `kotlin-compiler-embeddable` is what detekt/ktlint/IDE tooling historically used, but it's being abandoned — it's incompatible with the new Analysis API (relocated IntelliJ deps cause runtime failures), and detekt's own migration issue confirms this (github.com/detekt/detekt/issues/8027, closed 2026-05-10, moving to the plain `kotlin-compiler` artifact).

**K2 Analysis API has NOT solved the embeddable-frontend problem.** Its own docs state plainly: "the only officially supported use-case is IntelliJ IDEA plugin development... Standalone mode for command-line tool developers... is currently in development and subject to incompatible changes" (kotlin.github.io/analysis-api). So the hoped-for "lighter K2 frontend for external tools" doesn't exist yet as a stable thing — this is a real, current limitation, not FUD.

**But a real middle ground already exists and is production-proven**: ktlint and detekt's default (non-type-resolution) mode both run on the Kotlin compiler's **PSI** layer — the actual compiler AST — and explicitly need no classpath: "Parsing a Kotlin file does not require any knowledge about the project it belongs to" (blog.allegro.tech/2026/03/static-code-analysis-kotlin.html). detekt's opt-in "type resolution" tier requires `--classpath`/`--jvm-target` and only then unlocks rules annotated `@RequiresFullAnalysis` (detekt.dev/docs/gettingstarted/type-resolution) — this is the daemon-territory tier, same shape as jdtls. So: real compiler-grade parsing without classpath is possible for Kotlin (better than tree-sitter's 61.2% ceiling since it's the actual PSI tree, not an approximation), but it requires shelling out to a JVM — a new dependency class, not linked-in like tree-sitter. True semantic resolution stays classpath/daemon-only, and standalone Analysis API isn't a usable shortcut around that today.

## Scala

**Scalameta is mature, actively maintained, and Scala 3 is a solved, old problem, not an open gap.** Official docs state support for "Scala 2.12, 2.13, Scala 3, Scala.js, Scala Native." The Scala-3-parsing tracking issue (github.com/scalameta/scalameta/issues/2022, opened 2020) closed 2021 with the last edge case (infix type precedence) spun into #2315, closed 2022. Scalafmt has shipped `dialect = scala3` support since v3.0.0, in production use. Contrast with tree-sitter-scala, whose Scala 3 issue has sat open since 2021 with no maintainer response — this is a genuine, current, and structural gap for tree-sitter specifically, not just a maturity lag.

**Cost model is real and lightweight for the syntactic tier**: Scalameta's parser alone (no compilation) runs ~92k lines/sec, ~1.4MB memory per 100k LOC. Crucially, there's a **direct precedent for exactly monokl's use case**: `scalex` (github.com/nguyenyou/scalex, actively maintained, pushed June 2026) is explicitly "Scala code intelligence for coding agents. Zero Build Server. Zero Compilation." It uses Scalameta parse-only and documents the identical precision tradeoff monokl cares about verbatim: "No build, no classpath, no daemon... when two packages both define a class called `Config`, scalex can't tell which one `extends Config` refers to — that requires type resolution." Real numbers: 18.5k files/144k symbols in 2.7s cold / 349ms warm. Single maintainer, modest adoption (90 stars) — small but real and working.

**One more mitigation unique to Scala**: `scalafmt-native-image` (github.com/scala-cli/scalafmt-native-image) proves Scalameta-based tools can be GraalVM-native-image-compiled, meaning a Scalameta subprocess call could avoid the classic JVM cold-start tax entirely — a cost-model option with no confirmed Kotlin equivalent (no native-image build found for ktlint/detekt).

Real semantic Scala (SemanticDB) still requires actual compilation via a scalac/dotc plugin — that's the same daemon-territory tier as `ra_ap_hir`/jdtls, unchanged.

## Rust/WASM alternatives
Nothing usable on crates.io for either language, as expected: Kotlin has only `kotlin-parser` (WIP, v0.0.2) and the same tree-sitter grammars already evaluated; Scala has no real parser crate at all (`scala`/`serde_scala` are unrelated).

## Recommendation

Don't treat tree-sitter's ceiling as final for either language — a real **structural tier better than tree-sitter** exists for both, via each language's own compiler-grade parse-only mode (PSI for Kotlin, Scalameta for Scala), proven in production (ktlint; Scalafmt/Scalafix) and, for Scala, proven for this *exact* agent-facing use case by `scalex`. This is a distinct architectural shape from both tree-sitter (linked in-process) and a daemon (persistent warm state): a cold-per-invocation JVM subprocess, non-trivial but not daemon-scale. Scala's case is slightly stronger than Kotlin's — mature Scala 3 support since 2021-22, plus the native-image cost mitigation — where Kotlin's standalone Analysis API is explicitly unstable today per JetBrains' own docs. For both languages, true semantic/Exact-tier resolution genuinely requires classpath construction and belongs on the same deferred daemon/session-mode track as `ra_ap_hir` — that part of the original assumption holds. The new finding is that "Heuristic (tree-sitter) or bust" is not the full picture: a JVM-subprocess "Structural via real compiler parse" tier is a legitimate, evidence-backed option worth scoping as a near-term addition, separate from the daemon question.
