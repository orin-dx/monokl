## Findings (with real citations)

**1. OXC's own numbers** (github.com/oxc-project/bench-javascript-parser-written-in-rust): parse-only, `iter_with_large_drop` to exclude AST-teardown cost, single-thread + parallel, tested on M3 Max/M2/i7. Concrete: `cal.com.tsx` — OXC 3.4ms vs swc 14.4ms (4.28x) vs Biome 18.3ms (5.42x); `typescript.js` — OXC 26.4ms vs swc 91.0ms (3.45x) vs Biome 139.3ms (5.28x). Biome comparison explicitly flagged non-apples-to-apples (CST vs AST). **Tree-sitter is not in OXC's own comparison set at all** — there is no OXC-vs-tree-sitter-typescript number anywhere I could find.

**2. tree-sitter's own performance framing**: no official MB/s or lines/sec figures exist. The closest thing is an offhand maintainer comment in tree-sitter/tree-sitter Discussion #3413: a custom grammar parsed a 6k-line file in ~80ms, Python's grammar parsed 20k lines in ~120ms — presented as "comparable," not a rigorous benchmark. More telling: tree-sitter/tree-sitter Issue #1277 reports a 1.6MB JSON file taking **~1.2s for a full cold parse and ~0.7s to "re-parse" with zero edits**, consuming ~300MB for two trees. That 0.7s no-op-reparse number is direct evidence that tree-sitter's headline incremental advantage has a real floor — it is not free even in its best case.

**3. Root cause of tree-sitter slowness, where documented**: tree-sitter-haskell's 50x speedup (owen.cafe, corroborated by tree-sitter-haskell issue #41 "terrible performance on medium/big files") traced to the grammar's **external scanner calling malloc per-token** — a C-side allocation-pattern bug in that specific grammar, not an inherent property of the Rust↔C FFI boundary. Separately, Symflower's reported 36x speedup migrating JavaParser→tree-sitter (Go host) was driven by eliminating **cross-process/cross-language calls**, which is a different failure mode than Rust-to-C FFI. Rust's `extern "C"` FFI itself is near-zero-cost (direct calls, no marshaling) — unlike Python ctypes or JNI, which do pay real marshaling tax. Net: no evidence tree-sitter-python/tree-sitter-java pay an FFI-crossing tax in monokl's Rust host; if they're slow, the more likely culprit (per the Haskell case) is grammar-specific allocation behavior, discoverable only by profiling those two grammars specifically.

**4. Head-to-head native-vs-tree-sitter, same language**: I could not find any published benchmark of `ra_ap_syntax` vs `tree-sitter-rust`, a native Go parser vs `tree-sitter-go`, or Ruff's parser/RustPython vs `tree-sitter-python`. Ruff's own writeup ("The Evolution of Ruff's Parser") only benchmarks its hand-written parser against its own predecessor (~2x faster, 20-40% overall linter speedup) — never against tree-sitter-python. This is a genuine gap in public data, not something I'm approximating around.

**5. `gosyn`** (chikaku/gosyn, the real pure-Rust Go parser): README has zero benchmark numbers published.

**6. Comparable tools**: ast-grep's own "Optimize ast-grep to get 10X faster" post (10.8s→0.975s on TypeScript's repo, six rules) attributes the win entirely to regex-cloning and `potential_kinds` matching-logic fixes — it says nothing about parse cost scaling with repo size or cross-language differences, despite specific searching. difftastic's "boost difftastic by 4x" (QuarticCat) confirms the bottleneck was `Vertex` construction/memory layout in the Dijkstra-based diff graph (millions of vertices), not tree-sitter parsing — but the post never gives a parse-time-vs-diff-time percentage split, so I can't cite a number for "tree-sitter's share." codegraph's README states ~60 files/sec end-to-end indexing (parse+extract+write, not parse-only), no per-language breakdown despite searching.

## Practical implications / verdict

- **No public evidence supports differentiated cache-tier treatment by parser type on FFI-crossing grounds alone** — Rust-to-C FFI isn't the tax; grammar-specific C allocation patterns are, and that's only provable per-grammar via monokl's own profiling of tree-sitter-python/tree-sitter-java specifically.
- **Tree-sitter's "incremental" selling point is close to irrelevant to monokl's architecture** — this is well-supported, not just inferred: monokl never holds a previous tree to diff against (fresh process, no daemon), so it always pays tree-sitter's cold-parse path, and issue #1277 shows even the best-case no-op reparse path isn't near-zero on larger files. Monokl should budget tree-sitter grammars at their cold-parse cost, full stop.
- **Memory**: the one real data point (1.6MB JSON → ~300MB for two trees) suggests tree-sitter's peak memory during parsing can be nontrivial for large files; no fleet-scale (10k-50k file) tree-sitter-vs-native memory comparison exists publicly. This is worth a targeted monokl-internal check given the "no arena-borrowed data escapes" rule — the transient peak during conversion to owned `FileAnalysis`, not steady-state, is the risk.
- **Target numbers**: I recommend NOT porting any of the above into `benches/pipeline.rs` as target thresholds — none of these numbers are apples-to-apples with monokl's own file mix, and I want to flag plainly that I found no defensible way to convert "OXC 3-5x faster than swc/Biome" or "tree-sitter Python ~120ms/20k lines" into a monokl-specific per-language budget without measuring monokl's actual fixtures. The one directionally useful data point is codegraph's ~60 files/sec real-world indexing throughput (parse+extract+write combined) — extrapolated naively that's ~167s for 10k files, which should make monokl treat its own 15s cold-build target as unvalidated and likely optimistic until `pipeline_cold` is actually run, not as a number to relax the OXC/ra_ap_syntax/gosyn tier by default. I'd recommend the research log state explicitly: **the only trustworthy fix is running `benches/pipeline.rs` per-language on monokl's own fixtures** — every public number surveyed here differs enough in methodology (file size, hardware, what's measured) that none should be treated as monokl's target.
