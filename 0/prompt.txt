<result>## Research: How real semantic tools signal (or fail to signal) uncertainty, and what monokl's PrecisionUpgrader should do about it

**1. Neither LSP nor SCIP have a confidence field — verified directly.** Fetching the LSP 3.17 spec directly: `Location {uri, range}`, `LocationLink {originSelectionRange?, targetUri, targetRange, targetSelectionRange}`, and `ResponseError {code, message, data?}` — no field anywhere expresses confidence, ambiguity, or "multiple candidates considered." Fetching SCIP's actual `scip.proto`: `Relationship {symbol, is_reference, is_implementation, is_type_definition, is_definition}` and `Occurrence {range/typed_range, symbol, symbol_roles, syntax_kind, diagnostics, enclosing_range}` — same result, confirming the earlier SCIP finding and showing LSP is no better. The one structural signal LSP carries *incidentally* rather than by design: `textDocument/definition` and `textDocument/references` are typed to return `Location | Location[] | LocationLink[] | null`. A response with cardinality &gt;1 for a query that implies a single binding is a real, always-present ambiguity signal — but nearly every client discards it by taking `result[0]`.

**2. The common pattern across failure modes: internal degradation signals exist but are deliberately smoothed away before reaching the answer surface.** clangd is the clearest case, confirmed against Clang source: `RecoveryExpr` is a real, grep-able AST marker (`&lt;recovery-expr&gt;(...)`, per `StmtPrinter::VisitRecoveryExpr` and Clang's own AST-dump tests) — but clangd's `FindTarget` logic *deliberately resolves through it* to keep hover/go-to-definition looking normal, per explicit test comments like "no overload matches, but we have recovery-expr with the correct type." The degradation is invisible at the LSP layer by design intent, not oversight. TypeScript shows the same pattern differently: unresolved types collapse into the same `any` as a deliberately-untyped value, with no marker distinguishing "genuinely any" from "inference gave up." jdtls's classpath problems surface on a separate build/project-diagnostics channel rather than tainting the specific hover/definition response that used the broken classpath — a consumer reading only per-symbol answers never sees it. Kotlin and Scala are the informative *exceptions*: both eventually gained real, stable, machine-detectable sentinels precisely because the underlying ambiguity was too dangerous to leave silent — Kotlin's `T!` platform-type notation (documented, kotlinlang.org) and internal `ErrorType`/`ErrorTypeKind` (JetBrains/kotlin source); Scala's `diverging implicit expansion` string (Scala 2) and Scala 3's numbered `E172` "Ambiguous given instances" diagnostic. The pattern: whether a signal survives to the surface is a language-community design choice, not a property monokl can assume — so it must go looking for these sentinels itself rather than trusting a "successful" response.

**3. CHA/RTA/points-to literature gives a real, citable precedent, with one caveat.** The precision ladder is real and graded by cost/soundness tradeoff (Dean, Grove &amp; Chambers, CHA, ECOOP 1995; Bacon &amp; Sweeney, RTA, OOPSLA 1996; Andersen 1994; Steensgaard, POPL 1996), and Bravenboer &amp; Smaragdakis's Doop (OOPSLA 2009) proves this is operational, not just conceptual — it exposes context-sensitivity as a selectable, named parameter, i.e., analysis metadata about which tier produced a result. The closest citable principle for "make the tier explicit rather than pretend uniform confidence" is Livshits et al., "In Defense of Soundiness: A Manifesto" (CACM 58(2), 2015): document unsound design choices rather than hide them. Note this is about design-time disclosure, not literal per-fact provenance tagging — applying it to per-fact granularity is our extrapolation, not an existing paper's claim.

**Actionable rules for monokl's PrecisionUpgrader:**
1. Treat response cardinality as a signal: `definition`/`references` returning &gt;1 location for an ostensibly-unambiguous query → downgrade to `Structural`, emit a `Diagnostic` listing all candidates instead of silently taking `[0]`.
2. Maintain a per-backend sentinel table checked against *raw* diagnostics/type-strings, not the polished LSP layer: `&lt;recovery-expr&gt;`/dependent-type markers for Clang; `T!`/`ErrorType`/`ErrorTypeKind` or smart-cast diagnostic IDs for Kotlin; `E172`/"diverging implicit expansion" for Scala; co-occurring unresolved-import diagnostics on an `any`-typed hover for TS.
3. Cross-check project/build-level diagnostics each call (classpath, missing deps) — don't trust a clean per-symbol answer if the file's classpath is known-incomplete.
4. Classify by question type, not tool: closed-world nominal resolution with a language-guaranteed unique answer (Rust trait dispatch post-coherence, Java overload resolution) can earn `Exact`; open-world/coincidental-match questions (Go interface-implementer search, Kotlin extension resolution, C++ ADL with multiple viable candidates) cap at `Structural` even on compiler success, with the full candidate set attached as a `Diagnostic` rather than the tie-broken pick presented alone.
5. Never infer trust from response *shape* alone — since no protocol here carries confidence, silence from LSP/SCIP is absence of evidence, not evidence of correctness.
