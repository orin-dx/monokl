<result>## Research Findings: Multi-Backend Semantic Data Unification — Precedent Analysis

I verified primary sources directly (SCIP's actual protobuf schema, its design doc, CodeQL's real repo structure, rust-analyzer's documented LSP extensions) rather than relying on recalled summaries. One caveat up front: the shared web-search budget for this session was exhausted before I could run search queries, so everything below comes from direct WebFetch of primary documents, plus one narrative point I flag explicitly as unverified this session.

**1. Sourcegraph (LSIF → SCIP): unifies the reference graph, not the semantics.**
SCIP's own `scip.proto` and `docs/DESIGN.md` (github.com/sourcegraph/scip) show a deliberately narrow common core: a `Relationship` message with four boolean flags (`is_reference`, `is_implementation`, `is_type_definition`, `is_definition`) and an `Occurrence`/`SymbolInformation` pair keyed by a human-readable symbol string. That core generalizes honestly across languages because "X references/implements/defines Y" means roughly the same thing everywhere. Critically, SCIP does *not* try to unify deeper semantics. Its two real extension points are (a) `SymbolInformation.kind`, an enum that keeps growing per-language (`AbstractMethod` for Java/Kotlin, `Accessor` for Ruby, `Contract`/`Modifier` for Solidity) rather than staying generic, and (b) `documentation`/`Signature.language`, which are markdown/text blobs — meaning anything genuinely rich (a Rust trait bound, a Java checked-exception spec) degrades to unstructured prose, not structured data. DESIGN.md is explicit that indexers themselves stay per-language ("tooling for a language tends to be implemented in the same language... impractical to expect indexers to settle on a common implementation"), i.e., unification happens only at the wire format, never in the analysis itself. The lesson: SCIP's unification succeeded *because* it scoped down to navigation (def/ref/impl), not because it found a clever way to preserve full semantic richness — which is exactly the scope monokl's stated goal exceeds. (Sourcegraph's earlier live-language-server era being abandoned for operational/scaling reasons is a plausible history I hold from training but could not re-verify with a primary source this session after repeated 404s — treat that specific claim as unconfirmed, not load-bearing.)

**2. LSP / multi-language IDEs: common baseline + explicit typed escape hatch — the strongest direct precedent.**
VS Code's `vscode.languages.*` API (code.visualstudio.com/api/language-extensions/programmatic-language-features) defines ~18 standardized capabilities (hover, go-to-def, completions, etc.), and any server can implement them via LSP. But the protocol also has a built-in, exercised-at-scale extension mechanism: `experimental` capabilities and vendor-namespaced custom request methods. rust-analyzer is the concrete, documented example (rust-analyzer.github.io/book/contributing/lsp-extensions.html): it ships real custom methods — `rust-analyzer/expandMacro`, `rust-analyzer/viewMemoryLayout`, structural-search-replace, runnables — specifically because generic LSP hover/completion cannot carry macro expansion or memory layout facts. The doc even notes plain brace-matching needs "a real parser" for Rust's angle-bracket ambiguity, i.e., even trivial-seeming operations need language-specific logic. This is a production-proven pattern of exactly the shape monokl is considering: a stable generic core, plus optional, strongly-typed, per-language payloads that are additive, not a replacement.

**3. CodeQL: two coexisting patterns, both real, doing different jobs.**
CodeQL's own docs (codeql.github.com/codeql-standard-libraries) confirm it is genuinely per-language: separate libraries/dbschemes for C/C++, C#, Go, Java+Kotlin, JS/TS, Python, Ruby, Rust, Swift, with no shared universal schema — this maps directly onto monokl's existing `FileAnalysis`/`LangData` envelope-plus-variant shape, which is already the right template for *base* per-file analysis. But CodeQL also has a second pattern for cross-cutting concerns: `github/codeql`'s `shared/` directory (confirmed via repo listing) contains a language-agnostic `dataflow` module whose README states it provides "shared, language-agnostic CodeQL libraries" where the *algorithm* is generic and parameterized, and each language plugs in by implementing that interface with its own `Node`/CFG types. This is a shared-interface-with-per-language-implementation pattern, structurally different from a shared-data-schema pattern.

**Recommendation for monokl's daemon tier:**
Keep `FileAnalysis`/`LangData` unchanged for base per-file output — it already matches CodeQL's per-language-schema precedent correctly. For `PrecisionUpgrader` output specifically, don't invent one generic "upgraded fact" struct that every backend must squeeze into (SCIP's mistake, tolerable only because SCIP's scope is narrower than monokl's). Instead: (a) a small, honestly-shared core describing what an upgrade *is* — a resolved cross-file reference target (file+span), a resolved type as a display string — mirroring SCIP's boolean relationship flags, which generalize because they describe genuinely universal facts; and (b) a per-language, optional, additive extension payload (`Option&lt;RustUpgrade&gt;` / `JavaUpgrade` / `KotlinUpgrade`, structurally an enum sibling to `LangData`) carrying Rust trait-resolution chains, Java classpath provenance, Kotlin smart-cast state as real typed fields — never flattened into text. This mirrors both CodeQL's shared-interface pattern and rust-analyzer's proven custom-LSP-extension pattern, and the additive/optional shape matches this task's own framing of daemon data as a richness layer on top of base analysis, not a replacement. One further caution: GitHub's own stack-graphs project — a different attempt at a cross-language unifying resolution abstraction — was archived September 2025 (confirmed by a teammate's verified research this session), a real data point that betting everything on one clever universal resolution mechanism across languages is a genuine, demonstrated risk; per-language extension bags are the more conservative and evidence-backed choice. Note this analysis is about data *shape*; it found no evidence bearing on the PerCall/PerInvocation/Session lifetime axis one way or the other — that question is orthogonal to ingestion-model design.
