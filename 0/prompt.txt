I grounded this in monokl's own spec (`/Users/gabe/Projects/monokl/docs/monokl-spec.md`, ~325KB, no `.rs` source present yet — this is a spec-stage project) plus targeted web searches. Key discovery: **monokl's own benchmark suite doesn't yet measure this scenario** — `benches/pipeline.rs` has four criterion groups (`pipeline_cold`, `pipeline_warm_cache`, `dependents_warm`, `lite_symbols`) that are still empty stubs (spec line 2978). So any number below for "warm rebuild cost" is an inference from adjacent measured numbers, not a direct measurement — including inside monokl's own codebase.

**1. Tool-calls per session (grounded, but for single tasks, not full sessions).** SWE-bench trajectory data: SWE-agent/GPT-4 averages 14.71 turns (median 12, 75th pct 18) on full SWE-bench; Claude 3 Opus averages 12.71 turns on Lite. A cross-agent comparison found SWE-Agent 30.7, OpenHands 24.2, LiveSWE 13.5 tool calls/task (arxiv.org/abs/2405.15793; blog.nilenso.com/blog/2026/04/20/trajectory-shapes). These are single isolated bug-fix tasks, not full interactive sessions — real Claude Code/Cursor sessions chain multiple tasks and mix search calls with edits/bash/tests. I found no public number for "search-tool calls per real session" specifically — extrapolating from the above, **10–50+ search invocations per substantial working session** is a reasonable but unverified estimate.

**2. FOLD-step cost at 10k/50k files (estimated, not measured).** monokl's spec states: `WorkspaceIndex::build` cold target &lt;15s at 50k files (dominated by OXC parsing — the expensive part); disk-cache flush &lt;800ms; warm per-file `inspect` is 2.8ms but that number reflects the *in-process* DashMap cache (`WorkspaceSession`), which a fresh CLI subprocess never gets. For a fresh process with hot on-disk cache, the unavoidable per-invocation cost is: (a) `ignore::WalkBuilder` directory walk, (b) `cache.json` load/deserialize (size-capped at 100MB) plus stat()-based mtime/size dirty-bit checks per file, (c) the actual fold (`enricher.update`/`finalize` into `ImportGraph`/`SymbolIndex`) — all in-memory, no I/O. Since parsing dominates the 15s cold figure and fold-only work skips it, a defensible estimate is **roughly 100–500ms at 10k files, 300ms–1.5s at 50k files** — real, but a small fraction of the cold-build budget. Treat this as inference, explicitly flagged as unverified.

**3. Three options, compared:**
- **(a) Current (stateless CLI + per-file cache).** Cost = the fold estimate above × search-calls/session ≈ low seconds to ~1 minute of added latency across a whole session at 50k files — modest next to LLM think-time per round trip. Zero standing memory cost. Notably, monokl already tried and *reverted* an in-memory trigram index because it cost 600MB–1.2GB resident (spec line 2931) — direct internal evidence the team is memory-conscious about stateful designs.
- **(b) Daemon/MCP mode (codegraph-style).** Eliminates fold cost entirely for warm queries; adds daemon lifecycle, watcher, staleness banners, and a real memory footprint (the same category of cost monokl already rejected once). I sanity-checked codegraph's "25 min → under 1 min" claim directly against its v1.4.0 release notes (github.com/colbymchenry/codegraph/releases): it is **not** a general daemon-vs-stateless win — it's a SQLite write-journal/WAL fold-back I/O fix specific to throttled/slow disks (HDD, network, virtualized), and the release notes explicitly state "no change occurs on fast disks." That number doesn't transfer to monokl's fold-step question; it's a different bottleneck under different conditions.
- **(c) On-disk index snapshot + incremental patch.** Middle ground, but architecturally awkward today: `FileIdx` is deliberately *not* `Serialize` (spec line 2948, "compile-time guard against leaking across rebuild boundaries"), and `ImportGraphEnricher::finalize` depends on `file_index` being fully populated first — incremental patching would require loosening an invariant the codebase intentionally enforces.

**4. Recommendation.** Current design (a) is likely good enough at ≤50k files for typical sessions — a confident-ish claim given monokl's own stated latency targets already dwarf the fold cost. For 100k+-file monorepos or heavy multi-agent parallel search, (b) as an *optional* opt-in mode is the more scalable answer, not (c). But the honest first step, before any architecture change, is filling in the already-stubbed `pipeline_warm_cache`/`dependents_warm` benchmarks — that replaces this whole estimate with real numbers cheaply.
