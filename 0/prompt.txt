## How it works

Stack graphs extend the *scope graphs* framework from Eelco Visser's group at TU Delft (Visser et al.'s work on modular name resolution) with a stack mechanism. The core paper is Creager, "Stack graphs: Name resolution at scale" (arXiv:2211.01224 / DROPS OASIcs EVCS 2023.8). Name binding info is encoded as a graph where paths = valid bindings; resolving a reference is path-finding. The novel bit over plain scope graphs: compound references (`A.foo`) require *pausing* resolution of one name to resolve another — a natural stack operation, hence "stack graphs." Crucially, graph construction is **file-isolated** — each file's subgraph is built with zero visibility into other files — and cross-file resolution happens later via *partial-path stitching* (`stack-graphs` crate's `partial`/`stitching` modules). This is what gives it incrementality: unchanged files are never reanalyzed. (docs.rs/stack-graphs, arXiv:2211.01224)

## Cost to adopt

Real, published crates: `stack-graphs` (0.14.1, published 2021-05 through 2024-12-13) and `tree-sitter-graph` (0.12.0, the generic tree-sitter→graph DSL engine, still published under github.com/tree-sitter/tree-sitter-graph — NOT archived, last release Dec 2024). Defining a language means writing a `.tsg` file: pattern-match tree-sitter node types, emit graph nodes/edges/attrs (`push_symbol`, `pop_symbol`, scope edges), with `if`/`if none` guards for context sensitivity. I pulled the actual TypeScript definition (`languages/tree-sitter-stack-graphs-typescript/src/stack-graphs.tsg`) — **it's 6,297 lines**. That is substantially more code than a hand-rolled heuristic resolver would typically require, and it's write-only-once-you-learn-a-bespoke-DSL effort, not reusable Rust.

## Per-language maturity — the critical gap for monokl

Only **four** language definitions were ever built in github/stack-graphs: **Java, JavaScript, Python, TypeScript**. There is no Rust and no Go definition anywhere in the repo or its ecosystem. So for monokl's five languages, stack-graphs offers real prior art for exactly the ones where you're least stuck (TS) and nothing for Rust or Go, where the pain is worst.

Production usage is real, not vaporware: GitHub's Precise Code Navigation shipped on Python in Dec 2021 (github.blog/2021-12-09) and TypeScript in Mar 2024 (github.blog/changelog/2024-03-14), both explicitly "powered by stack graphs."

**However: github/stack-graphs was archived by GitHub on 2025-09-09** — read-only, "no longer supported or updated," with an explicit "if you wish to continue development, fork it." Last release was tree-sitter-stack-graphs v0.10.0, Dec 13, 2024. So GitHub built it, shipped it in production for 4 years, then stopped investing in the open-source side — no announced successor. (The generic `tree-sitter-graph` DSL engine lives on separately under the `tree-sitter` org and isn't archived, but the name-resolution-specific layer and all per-language definitions are frozen.)

## Precision model fit

No confidence/precision tiers exist anywhere in the docs or paper — resolution is a binary path-exists/doesn't-exist search. The one exploitable signal: ambiguous references naturally produce *multiple* candidate paths (unresolved overloads, dynamic dispatch), while unambiguous ones produce exactly one. Monokl could map "exactly one path" → `Exact` and "N>1 candidate paths" → `Structural`, but that mapping is something monokl would have to build itself — it isn't a first-class concept in the library.

## Verdict: skip, don't adopt

This is honestly still "per-language work," just relocated into an unfamiliar declarative DSL rather than Rust you already control — and the TypeScript definition suggests it's *more* total code than a heuristic resolver, not less. Combined with: (a) zero existing coverage for Rust or Go, monokl's hardest gaps; (b) the repo being archived with no successor, meaning any new `.tsg` work for Go/Rust would be unsupported from day one with no upstream to file issues against; (c) binary resolution requiring monokl to invent its own precision-tier mapping anyway — there's no case here for adoption over the current path.

The one place I'd flag as worth a second look, not a full adopt: monokl could fork/vendor the existing **Python and TypeScript** `.tsg` definitions as a reference implementation or even reused artifact for those two languages specifically (proven, production-tested rulesets, permissively licensed MIT/Apache-2.0) — but that's "borrow a finished asset for 2 of 5 languages," not "adopt stack-graphs as the resolution architecture." Given monokl's daemon-free CLI constraint is already satisfied by stack-graphs' file-incremental design, this narrow option is at least architecturally compatible if ever revisited — but I wouldn't spend cycles on it now.
