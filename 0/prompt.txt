Cloned github.com/ast-grep/ast-grep and read the core matcher, config/rule DSL, language registration, and CLI worker end to end (not just README/grep). Findings below.

**1. Query language / matching engine.** A pattern string is parsed by the *target language's own parser* (tree-sitter) then converted into a `PatternNode` tree — `Terminal`/`Internal`/`MetaVar` — via `convert_node_to_pattern` (crates/core/src/matcher/pattern.rs:223-245). So "compiling a pattern" is really "parse it as normal code, then walk the resulting CST." Matching walks goal vs. candidate nodes with `match_node_impl` (crates/core/src/match_tree/match_node.rs:8-55), using a generic `Aggregator` trait (match_tree/mod.rs:18-27) implemented once for the real `MetaVarEnv` and once for a cheap `ComputeEnd` counter — nice zero-cost reuse of one recursive algorithm for both "does it match" and "where does the match end." Ellipsis (`$$$`) handling is genuinely subtle: it clones the aggregator to *probe* the next goal node against each candidate before committing, specifically to stop failed metavar probes from leaking bindings into the real env (match_node.rs:153-182, with a regression test at pattern.rs:346-362 citing PR #2670). A `MatchStrictness` enum — `Cst/Smart/Ast/Relaxed/Signature/Template` (match_tree/strictness.rs:9-16) — is a tunable spectrum from "match everything including whitespace/comments" down to "match text only, ignore node kind entirely." This strictness knob is exposed per-pattern in the YAML rule (`pattern: {context, selector, strictness}`, crates/config/src/rule/mod.rs:199-211).

The YAML rule DSL (crates/config/src/rule/mod.rs) has three tiers: atomic (`pattern`, `kind`, `regex`, `nthChild`, `range`), relational (`inside`/`has`/`precedes`/`follows`, crates/config/src/rule/relational_rule.rs), composite (`all`/`any`/`not`/`matches`→ReferentRule for named+parameterized reusable utility rules, with cycle detection via `check_cyclic`). Relational rules take a `stopBy` (Neighbor/End/until-a-rule-matches) and an optional `field` that resolves to a tree-sitter field ID (`child_by_field_id`) for precise structural targeting, e.g. matching only inside a for-loop's `condition` field (relational_rule.rs:708-717 test). Rules pre-compute a `BitSet` of possible node-kind ids (`potential_kinds`, ops.rs:31-40, rule_core.rs:124-133) as an O(1) filter before running the real matcher on every node — this is ast-grep's only "index," and it's purely a kind-id bitset, nothing text-based.

**2. Multi-language architecture.** Adding a language is genuinely just: pick an expando char (to dodge `$` not being a valid identifier char in that grammar) and point a macro at a tree-sitter crate — `impl_lang!`/`impl_lang_expando!` (crates/language/src/lib.rs:64-148). There is no node-kind mapping layer, no per-language metavariable-extraction config beyond the single char choice. Consequence: rules are **not portable across languages** — `kind: function_declaration` only works for grammars that literally name that node that way, and ast-grep doesn't try to unify this. Quality gap between "flagship" and long-tail languages is real but narrow: Rust (crates/language/src/rust.rs) and Haskell (haskell.rs) have nearly identical, thin test suites (~5-10 pattern tests each) — the language's "quality" in ast-grep is really just whatever the upstream tree-sitter grammar's correctness is. There are explicit workarounds for known upstream grammar bugs, e.g. tree-sitter-typescript's wrong span for unnamed nodes (match_tree/strictness.rs:68-70, citing ast-grep#1419 and tree-sitter-typescript#306) — so grammar immaturity leaks directly into matcher correctness, which is exactly the class of pain monokl's OXC-for-TS decision was presumably trying to avoid.

**3. Ranking.** There is none. I grepped the whole repo for score/rank/bm25/relevance outside of the `transform` module (string-case transforms, unrelated) and found nothing — matches are pure boolean structural hits returned in file/scan order. No relevance sort, no dedup, no token budgeting.

**4. Performance.** Parallelism is `ignore::WalkParallel` (the ripgrep crate) with a classic multi-producer/single-consumer `mpsc` channel (crates/cli/src/utils/worker.rs:118-158) — not rayon (grepped, zero hits). Every invocation fully parses every file that survives the gitignore/glob filter (crates/cli/src/utils/mod.rs:143-144, `lang.ast_grep(file_content)`) — there is no persistent cache (mtime, content-hash, or otherwise) across runs; it's a stateless one-shot CLI. The only pre-match optimization is `Pattern::fixed_string()` (matcher/pattern.rs:188-205: recursively extracts the single longest literal-text child of a pattern) checked via plain substring `file_content.contains(...)` in crates/cli/src/utils/mod.rs:169-172 — but this runs **after** the whole file is already parsed into a tree; it only skips the rule-matching walk, not the parse itself. This is a materially weaker prefilter than monokl's grep-searcher-before-parse stage, and ast-grep has nothing analogous to a two-tier mtime/blake3 cache at all.

**Recommendations for monokl:**

1. **query/ module** — adopt a `MatchStrictness`-style tunable spectrum for the structural side of a query (at minimum a "signature" mode: match node kind, ignore literal text/comments). Monokl's BM25 text layer already handles fuzzy/ranked matching; a strictness knob would let the AST-evaluation stage relax without falling all the way back to pure text search.
2. **patterns/schema command family** — borrow the `inside`/`has`/`follows`/`precedes` relational vocabulary with `stopBy` (immediate neighbor vs. until-end vs. until-a-rule) and field-targeted matching (child-by-field-id). This is a clean, proven primitive for "structural pattern within structural context" that's more composable than kind+text alone, and maps well onto whatever OXC/ra_ap_syntax/tree-sitter field APIs each analyzer already exposes.
3. **query/ module (ellipsis/dedup correctness)** — if monokl's pattern matching ever supports multi-node capture (`$$$`-equivalent), copy the probe-before-commit technique (clone env, test, only commit on success) to avoid metavar binding leaks on failed backtracking — this was a real bug class in ast-grep (PR #2670) worth avoiding preemptively rather than discovering later.
4. **Not a design flaw, a validation** — ast-grep's `AnalyzerRegistry`-equivalent is cheap (macro + tree-sitter crate + one char) specifically because it only does structural match/no-match with no cross-language kind normalization and no relevance ranking. Monokl's heavier per-language cost (InspectEntry classifiers, BM25 boosts) is inherent to attempting semantic/ranked search rather than a gap to close — ast-grep offers no prior art for BM25 boosts, dedup, or token budgeting since it doesn't attempt any of that.
