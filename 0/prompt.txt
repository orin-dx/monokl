Here's a prompt you can hand to a read-only audit agent. I'd run it with bug-hunter on Sonnet, since it needs to read code and make judgment calls, and the results should come back ranked and with evidence, not as edits.

# Task: find over-engineering and non-idiomatic Rust in Callisto, read-only

Repo: `orin-dx/callisto` (a synchronous Rust release CLI, no async runtime). Do not edit files. Read AGENTS.md and docs/stability.md first.

## Why

A recent batch of work shipped machinery where the compiler or a smaller design would do. The owner's principle: in Rust, enforce invariants with types, traits and exhaustive matches so the compiler checks them; a test is the fallback for what types cannot see, and it should be small. Delete before adding. Every public surface (an error code, a JSON key, a flag) is permanent after 1.0.

## What to look for (concrete patterns we already found, so find more of them)

1. **Stringly-typed classification.** A hand-maintained list of strings that mirrors code (for example `USAGE_CODES` and a 233-code `RUNTIME_CODES` string in `crates/callisto-cli/tests/usage_exit_codes_tests.rs` deciding exit codes by matching error-code strings). Look for: matching on `code()` strings, `&[&str]` lists of names that parallel an enum, string comparisons where an enum or a trait method belongs.
2. **Tests that re-check what the type system guarantees.** A test that runs many binaries to assert a property a trait bound already enforces (for example `emit_report<R: Report>` already requires a schema version). Look for tests whose failure is impossible without a compile error first.
3. **Source-text scanning tests.** `include_str!`/`read_to_string` of `src/**` followed by string search. This repo deleted one before (#488). Also tests that grep docs or workflow files for strings that code could expose directly.
4. **Shell or text files where Rust works.** Scripts under `.github/tests`, `justfile` recipes, or `.txt` fixtures that compare data a Rust test could check with crates already in the tree (`insta`, `yaml-rust2`, `toml`, `serde_json`). Shell is right only for testing shell.
5. **Speculative generality.** Code for unsupported platforms (docs/stability.md says Windows is unsupported), hypothetical limits, configuration or parameters with one caller and one value, traits with one implementor and no test double, options nobody sets.
6. **Global mutable state** (`static` with `Mutex`/`OnceLock`) where returning data would do.
7. **Wall-clock or timing assertions** in tests. The repo's pattern is counting calls with a recording runner.
8. **Copies instead of a shared abstraction.** The same enum-to-string, error-to-exit-code or struct-to-JSON mapping written at several sites; many near-identical tests that a table (`rstest`) or one generic helper would replace.
9. **Surface area that need not be permanent.** Public error codes, JSON keys, flags or config keys added one-per-condition where a broader one with the detail in the message would do. Count how many exist per area.
10. **Wildcard arms and flag soup.** `_ =>` arms on our own enums, `bool` parameters or several booleans that can contradict (should be an enum), `Option` fields that are only valid together (should be one enum or struct), `String` where a newtype or validated type belongs (ids, paths, tags, SHAs).
11. **Reinvented crate functionality.** Hand-written parsing, edit distance, glob matching, retry, path normalisation or CLI handling where a crate already in `Cargo.toml` does it. Check `Cargo.lock` before claiming a crate is unavailable; do not propose adding a dependency unless the code is large and clearly worse.
12. **Comments, docs and tests that restate code** or narrate history (AGENTS.md forbids history comments).

## What is NOT a finding (refute before reporting)

- A test that drives the real binary to check observable behavior (exit code, stderr, files written, JSON shape). Those are the right kind.
- Code that is required by a documented 1.0 stability promise in docs/stability.md.
- Durability, safety or security invariants in AGENTS.md (for example atomic writes with fsync).
- A trait with several real implementors, or a test double that a test actually uses.
- Anything you cannot show is reachable or duplicated: read the callers.

## Method

Work area by area (`callisto-model`, `callisto-manifests`, `callisto-graph`, `callisto-cli`, `crates/*/tests`, `.github/tests`, `justfile`). For each candidate: read the code and its callers, then count (how many sites, how many lines of test versus production, how many callers). Use the repo's own tooling where cheap (`rg`, `cargo tree`, `wc -l`); do not run the full test suite.

## Report

Rank findings by **value of removing or simplifying** (lines removed, surface reduced, bug class made impossible), highest first. For each:
- Pattern number, file and line, and how many instances exist.
- Evidence (the caller you read, the count you took, the guarantee the type already gives).
- The lean replacement in one or two sentences, naming the type, trait, crate or deletion.
- Risk of the change and whether it touches a frozen 1.0 surface.
- Confidence (high, medium, low).

End with the five highest-value changes and a list of patterns you looked for and did not find. Under 800 words. Do not pad, and do not propose new features or new tests unless a deletion needs one.

Why it's built this way
- Concrete patterns from our own findings, so the agent has real examples to match against instead of generic advice.
- A "not a finding" section, because over-eager audits flag good tests and documented promises.
- Counts and callers required, so each finding has evidence and I can verify it before acting.
- Ranked by value of removal, with the lean replacement named, so the output turns straight into a short list of deletions.

How I'd use the result: read the ranked list, check the top items myself against the code (as I did with the earlier audits, whose first inventory missed a case), and then batch the approved deletions into one or two small PRs.

change #56 has insights:



<pasted_content id="bbdd">
### High finding

**Location:** `crates/monokl/src/analysis/nesting.rs:336`

For `for await (...)`, scanning `await` replaces `Last::HeadWord`, so this parenthesis is treated as an operand rather than a loop head. Inside an async function, repeating `for await (const x of xs)\n` therefore resets the estimate at every next loop (`nesting.rs:325–331`), admitting deeply nested loop bodies to the fixed-stack parser (`ts/parse.rs:77,91`) and risking process-aborting overflow. Preserve the loop-head state through `await`.
</pasted_content id="bbdd">



<pasted_content id="bbdd">
### High finding

**Location:** `crates/monokl/src/analysis/nesting.rs:268-271`

In a `.tsx` file, `export const x = ` followed by 300,000 `<a>;` openings, `x`, and 300,000 `</a>;` closings is valid source below 4 MiB, but every text semicolon resets the accumulated angle cost. This admits unbounded JSX recursion into the fixed-stack parser and recursive visitor (`ts/parse.rs:91,639`), allowing a process-aborting stack overflow. Preserve JSX nesting charges across punctuation in JSX text.
</pasted_content id="bbdd">



<pasted_content id="bbdd">
### Medium finding

**Location:** `crates/monokl/src/analysis/nesting.rs:524-526`

A valid `.ts` expression containing 10,000 repeated `of / [` prefixes, matching `]` closers, and 3 MiB of trailing spaces passes both caps, but each slash rescans the entire remaining suffix before `regex_end` returns `None`. This causes over 30 billion byte inspections in the pre-scan invoked by `ts/parse.rs:74`, severely delaying search. Cache failed lookahead or otherwise bound total scanning work to the source length.
</pasted_content id="bbdd">
