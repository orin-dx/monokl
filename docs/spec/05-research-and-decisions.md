# Research & Decisions Log (pre-implementation)

Findings from a competitive deep-dive (colbymchenry/codegraph), follow-on research into ranking, eval methodology, scale targets, and language support (Rust/Python/Go/Java), and a Rust-idiom audit of the verbatim code in Parts 1-4 — run before any of this spec gets built, so assumptions get stress-tested on paper instead of in a PR review. Two compile-breaking gaps this audit found (a `LanguageAnalyzer` trait missing methods it's called with, and four `MonoklError` variants that were constructed but never declared) are fixed directly in [01-core-architecture.md](./01-core-architecture.md) and [03-multi-language-platform.md](./03-multi-language-platform.md) — this log records why.

# Part 5: Pre-implementation research amendments

> Added before any of Parts 1-4 have been built. A competitive deep-dive against colbymchenry/codegraph (a mature, production multi-language code-intelligence tool) plus targeted follow-on research were used to stress-test this spec's assumptions before they calcify into code. Two categories below: fixes already applied directly to the sections above, and decisions/open tracks that change what future PRs should do.

## 1. Fixes applied in this document

- **§Python fidelity, problem 5** (type annotation resolution): `CapabilityPrecision::Approximate` was not a real variant of the enum defined in §11 (`Unsupported < Heuristic < Structural < Exact`). Corrected to `CapabilityPrecision::Heuristic`.
- **§Section 6, `STOP_WORDS`**: added `crate`, `self`, `super`, `dyn`, `async`, `await`, `unsafe` — near-universal Rust tokens the original TS/Rust-tuned list omitted, found by tracing the tokenizer's actual splitting rules against real Rust source rather than assuming coverage.
- **`LanguageAnalyzer` trait, §11**: `language_id(&self) -> LanguageId` and `capabilities(&self) -> AnalyzerCapabilities` were both fixed at one value per analyzer _instance_ — a real gap once §10's generic fallback-tier analyzer owns several languages with genuinely different ceilings in one instance (C reaches `Structural`, C++ is capped at `Heuristic`). Without this fix, §10's own design doesn't actually compile against the trait it's specified to implement. Fixed to `languages(&self) -> &[LanguageId]`, a new `language_for(&self, path: &Utf8Path) -> Option<LanguageId>` resolving which specific language a path maps to, and `capabilities(&self, language: LanguageId) -> AnalyzerCapabilities`. Every call site in `03-multi-language-platform.md` updated to match: `TsAnalyzer`/`RustAnalyzer`'s impls, `AnalyzerRegistry::supports_language`, and `query_support.rs`'s `resolve_canonical_source`/ `add_precision_diagnostic`/`require_precision_capability`. `LanguageId` itself gained the §10 fallback-tier variants (`C`, `Cpp`, `Bash`, `CSharp`, `Ruby`, `Php`) and the §10-refined `Heuristic`-only Kotlin/Scala variants, none of which existed on the enum before this pass despite being referenced throughout §10/§12.
- **`MonoklError::Json` and `StaleDiskCache` Display literals (SPEC-001 AC-011, AC-020)**: `Json`'s literal corrected from `"json serialization failed"` to `"json parsing or serialization failed"` at `01-core-architecture.md:222`, since one of its 8 real call sites (`persist::load_cache`'s cache-deserialize) is a parse failure the old text mischaracterized as a serialization failure. `StaleDiskCache`'s literal corrected from `"disk cache is stale (version or config mismatch); run \`mnkl init --rebuild\`"` to `"disk cache is stale (version or config hash mismatch)"` at `01-core-architecture.md:228`, removing a reference to a CLI subcommand (`mnkl init --rebuild`) that does not exist anywhere in this spec corpus -- see `07-edge-cases-and-failure-modes.md` Part 1, finding #6, which first flagged this as dead-code-referencing-a-nonexistent-command. Both corrections were made directly in `01-core-architecture.md` per this repo's own `AGENTS.md` ("fix it in the spec file too ... don't fix it only in code"), not silently left as a code-only divergence.

## 2. Adopted, not yet implemented

- **Add `oxc_semantic` to the `lang-ts` feature's dependency set**, versioned in lockstep with `oxc_parser`/`oxc_ast`/`oxc_span`/`oxc_allocator` (same version string — no separate compatibility matrix). `SemanticBuilder::build(&program)` runs against the same per-file `Allocator` arena the parser already uses and produces a `Semantic` result (scope tree + symbol table: `SymbolId`/`ScopeId`/`Reference`, real shadowing/hoisting/TDZ-aware binding). This replaces regex/text-scanned local-usage resolution in `refs`/`definition` with genuine scope-aware resolution for within-file references — closing the exact class of technical debt codegraph's own maintainers flag as their worst (a 20+-resolver heuristic confidence cascade). `oxc_semantic` is file-scoped: it does not replace `oxc_resolver` for cross-file specifier resolution, it upgrades what feeds into that combination. Output must be converted to owned data before the arena drops, same discipline as the AST conversion already documented in §17.
- **Build an eval harness before further ranking/tuning decisions are made on faith.** BM25's `K1=1.5`/`B=0.5` and the token-budget defaults are carried over from Probe's prior tuning (§29) and are unvalidated for monokl specifically. Minimum viable harness: two layers, not one — (a) a deterministic retrieval eval (RepoBench-R- or CodeSearchNet-style recall@k/MRR) run on every commit, and (b) a properly-powered agent A/B (model/effort pinned and logged, ≥5 runs per condition reporting median + IQR, ≥10 repos with a task list frozen before either arm runs). Report token and dollar-cost deltas _separately_, broken out by cache-read vs. fresh-input token mix — codegraph's own published cost-savings claim reversed under independent replication specifically because token/call reductions and dollar cost decoupled when its context payload shifted from many cheap cached reads to fewer expensive fresh reads. Cheapest first step: fill in the four already-stubbed `benches/pipeline.rs` criterion groups (`pipeline_cold`, `pipeline_warm_cache`, `dependents_warm`, `lite_symbols`, §29) — every cold/warm latency target asserted elsewhere in this spec is currently unmeasured, including in monokl's own benchmark suite.
- **Add worked query examples and a tolerant natural-language fallback** to the `search` command's tool-facing description. The `+/-/"phrase"/regex:` grammar itself is confirmed well-matched to how coding agents actually call lexical search tools (every purpose-built tool surveyed — Claude Code's Grep, Cline, Continue.dev, GitHub's MCP `search_code` — uses regex/qualifier syntax; natural language appears only as a separate, explicitly-labeled semantic tool elsewhere, never mixed into a grep-style tool's input). The gap is discoverability, not grammar: detect question-like input (`where`/`how`/`?`, five-plus words, no `+`/`-`/`regex:` modifiers) and degrade gracefully to bare-optional-term matching instead of erroring, since agents will occasionally route full questions to any tool that sounds like "search."
- **Add a `TraitImplEnricher` / `TraitImplIndex`** for Rust — a reverse index (`FxHashMap<String, Vec<(FileIdx, usize)>>` keyed by trait name, pointing at implementor sites) inverting the per-struct `RustStructEntry.trait_impls: Vec<String>` across the whole corpus. This is the structural signal that upstream discovery (interface/trait → implementors — controllers, services, handlers wired through a trait) actually depends on, and monokl's current design has no such index anywhere. Follows the exact `SymbolIndexEnricher` shape already in this spec: `update()` pushes one `(FileIdx, decl_offset)` per trait per file; `finalize()` sorts each bucket by `(FileIdx, offset)` for determinism. `petgraph` was considered and rejected for this and for `ImportGraph` generally — its `NodeIndex` would either leak as the public handle (undermining `FileIdx`'s deliberate non-`Serialize` guard) or need wrapping anyway for no gain, and it pulls in dependencies (`fixedbitset`, `hashbrown`, `indexmap`) for graph algorithms (SCC, Dijkstra) monokl doesn't use; the existing hand-rolled `FxHashMap` adjacency-list approach already matches what rust-analyzer's own `trait_impls_in_crate_query` and rustdoc's implementors-list generation do structurally (a dedicated reverse index built during a full pass), differing only by the Salsa incremental caching this spec deliberately forgoes. "Upstream discovery" for a trait `T` then composes three existing/new indices — no fourth graph structure needed — via a capped BFS: `TraitImplIndex` → implementor sites, cross-referenced against `SymbolIndex` for usage sites, expanded through `ImportGraph` reverse edges. That BFS should adopt the same hardening codegraph's own `GraphTraverser` needed in production: an `FxHashSet<FileIdx>` visited-set checked at enqueue time (not just dequeue), an explicit depth limit, and a result cap checked at every push site rather than only the loop head. Surface a cap-hit as a first-class, matchable outcome — extend `MonoklError` with a non-fatal `TraversalCapExceeded { visited: usize, cap: usize }` variant, returned inside a `TraversalReport { sites: Vec<_>, truncated: bool }` rather than silently truncating a bare `Vec`. The same bounded-BFS pattern generalizes to any of this spec's existing traversals (`dependents`/`imports_of`, impact-radius-style queries) that don't yet have explicit cap enforcement at every site.
- **Generalize `TraitImplIndex` toward SCIP's `Relationship` shape, not its wire format** (full research in §7). Tag each `(FileIdx, usize)` entry with which relationship kind it represents (`is_implementation`/`is_type_definition`/`is_reference`/`is_definition`, mirroring `scip.proto`'s `Relationship` message) instead of assuming "implementation" for everything — free forward-compatibility for non-trait-impl relationships later, at no cost now. Do not adopt SCIP's symbol-moniker grammar as a `FileIdx` replacement, and do not treat rust-analyzer's own SCIP output as a source of this data today — its CLI hardcodes `relationships: Vec::new()` as of this research pass (verified against `crates/rust-analyzer/src/cli/scip.rs`), so the one crate that could plausibly supply this for free currently supplies nothing.
- **An RTA-style instantiation filter over `TraitImplIndex`** (literature grounding in §8) — cross-reference implementor types against observed struct-literal/constructor sites already collected by `SymbolIndex`, pruning "declared-hierarchy" hits down to "declared and actually constructed" ones. Same cost order as the existing CHA-shaped pass already described above; a real precision improvement, not a new `CapabilityPrecision` tier.
- **Optional `.scip` file ingestion as a precision-upgrade path, not a dependency** (§7). If a `.scip` index already exists in-repo (produced out-of-band by `scip-typescript`/`scip-java`/ `rust-analyzer scip`), an optional reader via the official `scip` crate (v0.9.0, one real dependency, `protobuf = "=3.7.2"`) could promote matching occurrences from `Heuristic`/ `Structural` to `Exact`. Never invoked live, never required — a batch precompute a user opts into, not a monokl dependency.
- **A `MatchStrictness`-style spectrum for the query pipeline's structural-evaluation stage** (§7), modeled on ast-grep's `Cst/Smart/Ast/Relaxed/Signature/Template` dial — lets a query relax from "match kind, text, and trivia" down to "match kind only" without falling all the way back to plain text search. Pair with ast-grep's relational-rule vocabulary (`inside`/`has`/`follows`/ `precedes`, each with a `stopBy` of immediate-neighbor/until-end/until-a-rule, plus field-targeted matching via `child_by_field_id`) for the `patterns`/`schema` command family (Part 2) — a composable primitive for "structural pattern within structural context" that's a real step up from kind+text matching alone.
- **A content-hash-based move detector for the `diff` command** (§7) — hash each named top-level declaration by normalized subtree content and match across the two trees by hash before doing any positional diffing. Cheap, and difftastic — the most mature tree-sitter-based structural differ surveyed — still doesn't have this (`Wilfred/difftastic#508`, opened 2023, unimplemented) — a real edge over the strongest prior art examined. Also adopt difftastic's per-language `atom_nodes`/`delimiter_tokens`-equivalent config (which node kinds are leaves for diff purposes, which delimiters pair) — monokl's tree-sitter-backed analyzers (Python, Java) will hit the same false-diff bugs without it.
- **A generic tree-sitter fallback tier, launching with C, C++, Bash, and C#** (full research in §10). One `LanguageAnalyzer` impl handling all four via a small internal per-language config table, `Heuristic`/`Structural`-only, no bespoke `InspectEntry` classifier per language — same one-impl-per-language shape `AnalyzerRegistry` already dispatches on, just with that one impl owning N languages instead of one. C++ launches capped at `Heuristic` specifically (not `Structural`) given a real, currently-unresolved grammar ambiguity in `tree-sitter-cpp` (statement parsing is expression-vs-declaration-ambiguous without type info the parser never sees). `CapabilityPrecision` must be reported per-language-instance inside this one analyzer, not per-impl — the existing five analyzers never needed this since each already owns exactly one language.
- **Budget tree-sitter-backed languages (current and any future fallback-tier additions) at their cold-parse cost, with no incremental-reparse credit** (full research in §11). Monokl never holds a previous tree to diff against — every invocation is a fresh process reading from cache, not a live-edit session — so tree-sitter's headline incremental-reparse advantage doesn't apply to monokl's actual usage pattern. *Conditional, per §15(b): once Part 8's long-lived `Workspace` exists, a `Session` does hold the previous tree, and this budget should be re-measured for that lifetime only.* Do not port any externally-published parser benchmark number (OXC's own, tree-sitter's informal maintainer figures, codegraph's ~60 files/sec) into `benches/pipeline.rs` as a target threshold — none are methodology-comparable to monokl's own file mix. The stubbed `pipeline_cold` benchmark (§2 above) is the only trustworthy source of a real number here; until it runs, treat this spec's existing ~15s cold-build target as unvalidated and plausibly optimistic, not as a number to relax.
- **An optional, runtime-detected Clang-gated analyzer for C and C++** (full research in §12), preferred over `libclang` FFI: shell out to `clang -Xclang -ast-dump=json -fsyntax-only` and deserialize via `clang-ast` (dtolnay) rather than linking `clang-sys` — no header/version matching, just "is `clang` on `PATH`." Falls back automatically to the §10 tree-sitter tier when Clang isn't found. Capped at `Structural`, not `Exact`, without a real compilation database present. This is the concrete answer to §10's open "C++ graduation" question — not a bespoke native-Rust parser (C++'s parsing ambiguity is a real semantic-analysis problem no pure-Rust grammar-engineering effort can plausibly solve better than tree-sitter already does), but an optional real-compiler-frontend tier.
- **An optional JVM-subprocess `Structural`-tier analyzer for Kotlin (compiler PSI) and Scala (Scalameta)** (full research in §12) — both are compiler-grade parse-only modes that need no classpath, clearing well past tree-sitter's ceiling for each language (Kotlin's grammar tops out at 61.2% structural accuracy; Scala's has no Scala 3 support at all). Real production precedent for both (ktlint/detekt's default mode; Scalafmt/Scalafix; and for Scala specifically, a direct precedent for monokl's own use case, `scalex` — "Scala code intelligence for coding agents. Zero Build Server. Zero Compilation."). True semantic resolution for either language still needs a real classpath and stays on the same deferred daemon/session-mode track as `ra_ap_hir` (§4) — this tier is a new middle rung, not a shortcut past that.

## 3. Validated — no change made

- **`ra_ap_syntax` stays over `syn`** for the Rust structural tier. `syn::File::parse` fails fast at the first bad token with no partial-parse mode (the documented pattern is to emit `compile_error!` and stop); `ra_ap_syntax` is IDE-designed to always produce a tree, tagging error nodes instead. Monokl searches real working trees — WIP branches, merge-conflict markers, mid-edit files — where a single syntax error under `syn` would blank out symbol extraction for that entire file. No published throughput number for `ra_ap_syntax` parse-only performance exists anywhere (confirmed absent even in rust-analyzer's own benchmark suite); the error-recovery gap is the deciding factor regardless of the unquantified speed cost.
- **`tree-sitter-python` stays over Ruff's Rust-native parser crates** for `lang-py`. `ruff_python_ast`/`ruff_python_parser` are explicitly disclaimed by Ruff itself as unstable internal implementation details (still `0.0.x`, "frequent breaking changes" in their own words) — not a publishable dependency contract. tree-sitter-python's actual open issues cluster around bleeding-edge type-hint syntax (PEP 604/695), not the decorators/classes/ `__all__` handling the Python fidelity questions above actually need.
- **`WorkspaceIndex::build`'s parallel-analyze-then-sort-by-path pattern needs no upgrade** to a strict sequential-commit scheme. That extra machinery exists in comparable tools only to compensate for heuristic name-matching resolvers that disambiguate same-named candidates by database insertion order — monokl doesn't have that failure mode, because `oxc_resolver` and `resolve_rust_path` resolve each import to a specific file deterministically (no name-based candidate list to tie-break), and everywhere else multiple candidates can occur (`SymbolIndex::lookup`, `definition`'s re-export ranking) this spec already sorts on explicit keys — path, line, re-export flag — not insertion order.

## 4. Open investigation tracks — not decided

- **Salsa** (rust-analyzer's incremental-computation engine) as monokl's own memoized query cache, decoupled from any `ra_ap_hir` decision. Real standalone precedent exists (Astral's `ty` Python type checker, Biome's analyzer layer both use Salsa independent of rust-analyzer's own queries) — monokl could define its own queries (symbols-for-file, postings-for-term) memoized on content hash without ever loading a crate graph, a materially lighter proposition than embedding `ra_ap_hir` wholesale. Worth a scoped spike, tracked separately from the item below.
- **`ra_ap_hir` integration and any persistent daemon/session mode are a coupled pair.** `ra_ap_hir`'s `Semantics` gives real Rust name resolution and type inference, but needs a populated `HirDatabase` via `cargo metadata` + crate-graph construction — a cost pegged by rust-analyzer's own maintainers at roughly 5 seconds per 100 crates just waiting on rustc. That cost model fits a warm, long-lived process, not a cold per-invocation CLI. Symmetrically, a persistent index/daemon mode (mirroring codegraph's watcher architecture) is *hypothesized* to earn its own cost only past roughly 50k files — below that, the current stateless design's per-invocation fold cost (re-aggregating already-cached per-file analyses into `ImportGraph`/`SymbolIndex`, not re-parsing) is estimated at 100-500ms at 10k files and 300ms-1.5s at 50k, a small fraction of the 15s cold-build budget. Both the estimate and the threshold are unmeasured (§15(c)): no external source corroborates a crossover that high, and the nearest data point (codegraph persisting at 4,400 files) cuts the other way. Part 8 §13's benchmark is the test. Revisit both together, after the eval harness (§2) and the stubbed benchmarks (§2) produce real numbers — not before.
- **Over-fetch-then-rerank staging** in the search pipeline is the one ranking pattern with real cross-tool evidence (Continue.dev, codegraph, general two-stage IR) beyond what §Section 8 already does; a small import/reference-proximity nudge as a minor multiplier is defensible. Scope not yet decided — do not build a full Aider-style PageRank-over-symbols system as a primary rank driver on this basis; Aider's own repo-map algorithm has no published evidence it beats simpler baselines despite being well engineered.

## 5. Rejected

- **Embedding-based semantic rerank by default.** No code-specific evidence shows it beats lexical+structural signals for single-codebase retrieval (identifiers matter more than paraphrase within one codebase), and every tool surveyed that uses it depends on server-side vector-DB infrastructure — none of the local-first CLI tools examined run it by default. If ever added, gate behind an explicit opt-in flag; it is not this spec's default posture. The stronger version of this argument is a decade of established code-intelligence practice — CodeQL and LSIF/SCIP have relied on exact, compiler/AST-derived graphs rather than embeddings for precise code intelligence long before RAG was a term. A small, weakly-evidenced preprint (Chinthareddy, "Reliable Graph-RAG for Codebases," arXiv:2601.08773 — single-author, no institutional affiliation in this field, unreviewed, n=45 questions across 3 repos, no independent replication; vetted and found directionally-consistent-but-not-rigorous) reports numbers in the same direction (a deterministic AST graph answering 43/45 benchmark questions vs. 31/45 for vector-only similarity, and LLM-generated dependency graphs missing 377 of 1210 files at indexing time while costing 70-150× more to build than deterministic extraction) — cite it only as an early, consistent data point, not as load-bearing proof. Its own described "bidirectional traversal" is, per the paper's actual source, a single 1-hop successor/predecessor expansion rather than genuine multi-hop reasoning — worth knowing before assuming it validates more traversal depth than it actually tested. Independent evidence either way against ever LLM-generating the workspace graph as an alternative to parsing it deterministically — a design path this spec never considered but is now explicitly closed off, on the stronger CodeQL/SCIP grounding rather than the preprint alone.
- **stack-graphs / tree-sitter-graph as monokl's resolution architecture** (full research in §7). github/stack-graphs was archived by GitHub in September 2025 with no successor, and language definitions were only ever built for Java/JS/Python/TypeScript — none for Rust or Go, monokl's two hardest resolution gaps. The one definition inspected in full (TypeScript, `tree-sitter-stack-graphs-typescript/src/stack-graphs.tsg`) is 6,297 lines — more code than a hand-rolled heuristic resolver, just relocated into an unfamiliar DSL — and resolution is binary (a path exists or it doesn't), with no precision-tier concept to map onto `CapabilityPrecision`. Narrow option left open, not adopted: fork the existing Python/TypeScript `.tsg` rulesets as a reference implementation for those two languages specifically, since they're production-tested (GitHub's own Precise Code Navigation) and permissively licensed — not worth spending cycles on now.
- **SCIP as monokl's symbol-identity scheme or an output format** (§7). The moniker grammar (`<scheme> <package> <descriptor>+`) buys nothing over the existing internal `(FileIdx, usize)` keys and adds real string-parsing/escaping surface monokl doesn't need. Emitting SCIP is also rejected for now: real non-Sourcegraph consumption is limited to a handful of well-resourced orgs (Meta's Glean, Mozilla's Searchfox), and the schema has no field for expressing `Heuristic`-tier confidence honestly — emitting it would mean silently overclaiming precision.
- **difftastic's Dijkstra-over-a-token-graph algorithm as the `diff` command's core** (§7). It solves a harder, more general problem (minimal, human-readable textual diff) than monokl needs (a semantic "what changed" summary for an agent) — its own published 4x-speedup writeup is almost entirely vertex-memory-layout engineering, not algorithm choice. A shallow top-down structural match (match named declarations by name+kind, recurse only into matched pairs, treat the rest as added/removed) is the right-sized approach instead; see §2 for what's still worth borrowing from difftastic.
- **k-CFA-style call-flow analysis for any resolution tier.** Full literature grounding in §8 — it targets first-class-closure flow in dynamically-typed/functional code, is EXPTIME-hard for any static k>0, and degrades badly on OO-flavored dispatch specifically (the case monokl actually needs), per Might, Smaragdakis & Van Horn's "k-CFA Paradox" result. Not a fit anywhere on this spec's precision ladder.

## 6. Language roadmap

The v1.2 target of C# is dropped. Priority beyond `lang-ts`/`lang-rs`/`lang-py` is now driven by general market reach rather than one company's internal stack. Go and Java were evaluated as the leading candidates; both get a native `Structural`-tier analyzer, but via different parsers, for reasons specific to each language's actual crate ecosystem (checked directly against crates.io, not assumed):

**`lang-go`** — **`gosyn`** ([chikaku/gosyn](https://github.com/chikaku/gosyn)) is a real, viable native Rust parser: 152k+ downloads, weekly commits, MIT-licensed, confirmed Go 1.18+ generics support (`parse_type_parameters`, generic instantiation/pointer types both present in source and tests). This is the strongest native-parser candidate found across every language evaluated this session — unlike Python and Java, Go did not need to fall back to tree-sitter. `go/packages.Load` (real semantic analysis) is daemon-only by the same argument as `ra_ap_hir`: a 20k-package monorepo took 3m26s cold to load ([golang/go#69523](https://github.com/golang/go/issues/69523)), and even a warm gopls daemon took 10+ seconds to serve a new client on a 2,047-package repo ([golang/go#48829](https://github.com/golang/go/issues/48829)). Import resolution is genuinely easier than Rust's for the common case — no macros, no monomorphization, and a `go.mod` module directive plus import-path-prefix-stripping gives a project-relative directory directly (mirror `resolve_rust_path`'s shape, but simpler). Two gaps explicitly out of scope for v1: `go.work` multi-module workspaces (unhandled — root `go.mod` only), and `//go:build`-tag-gated files (gopls itself cannot auto-detect arbitrary build tags beyond the `_linux.go`-style filename convention; a structural tool will see phantom duplicate symbols across tag-gated variants of the same declaration). `CapabilityPrecision::Structural`. Tokenizer: extend `STOP_WORDS` with `func`, `package`, `chan`, `defer`, `select`, `range`, `go`, `iota` when `lang-go` lands (`new`/`super`/`interface`/`struct` are already covered by existing entries).

**`lang-java`** — no viable native Rust parser exists (`oak-java` and `java-lang` are both single-maintainer, pre-1.0, near-zero organic adoption; no `java-parser`/`javasyn` crate exists at all). `tree-sitter-java` is the correct choice, same conclusion as Python, and independently confirmed by codegraph's own "native, no-WASM" performance kernel — even it compiles `tree-sitter-java` natively via FFI rather than replacing the grammar. Real semantic analysis (JDT/`javac` classpath resolution via `jdtls`) is daemon-only, with documented real-world pain at scale (20s cold completion on multi-million-line projects vs. 1-2s warm, [eclipse-jdtls/eclipse.jdt.ls#3202](https://github.com/eclipse-jdtls/eclipse.jdt.ls/issues/3202); OOM crashes importing 3000+-file projects, [#1469](https://github.com/eclipse-jdtls/eclipse.jdt.ls/issues/1469)) — unlike Rust/Go, there is no established lightweight semi-semantic tier for Java at all; the field is bimodal. Non-wildcard imports (`import com.foo.Bar;`) give an unambiguous textual simple-name→FQN mapping, easier than Go's or Rust's equivalent case — but the majority of real-world Java imports (JDK, Spring, Guava, Lombok) resolve to JAR-only symbols with no local source, a structural wall no non-JVM tool can cross, and one that bites harder in Java than in Rust/TS/Go because idiomatic Java leans more heavily on external-library symbols per file. Worth the same order of hand-tuning investment codegraph put into its own Java extractor (334 lines — its most hand-tuned language after TS): specifically Lombok-generated-member synthesis (`@Getter`/`@Setter`/`@Data`/`@Builder` → synthetic getter/setter/`equals`/`hashCode` nodes), without which Lombok codegen silently breaks call-chain resolution. No Maven/Gradle multi-module resolver exists even in mature production tools (a documented gap, not an oversight) — cap that specific case at `Heuristic`. `CapabilityPrecision::Structural` for same-module declarations and non-wildcard local import resolution; `Heuristic` for wildcard imports, cross-JAR external symbols, and multi-module source-root inference; `Exact` explicitly out of scope (daemon-only). Tokenizer: extend `STOP_WORDS` with `public`, `private`, `protected`, `static`, `final`, `void`, `implements`, `package`, `throws`, `abstract`, `instanceof`, `null` when `lang-java` lands (`new`/`super` are already covered).

A related architectural question raised by studying codegraph (which reaches 30+ languages via one generic tree-sitter-walking engine with thin per-language config, versus monokl's fully-native per-language analyzer approach): whether to add a generic tree-sitter fallback tier — `Heuristic`/`Structural` precision only, search/symbols capability without a bespoke semantic layer — for languages beyond this list. **Decided: yes**, scoped tightly — see §10 for the full research, launch set (C, C++, Bash, C#), and the graduation path back to a dedicated Go/Java-style analyzer for any fallback-tier language that earns it. Go and Java themselves never needed this tier; both justify dedicated hand-tuned analyzers on their own merits independent of it.

## 7. Prior-art survey: SCIP, stack-graphs, ast-grep, difftastic

Four more tools/protocols investigated for design influence after the codegraph deep-dive, each via genuine primary-source research (real `.proto`/source files fetched and read, not documentation summaries taken on faith). Verdicts feed §2 and §5 above; full detail recorded here since all four were researched as one batch.

**SCIP** ([sourcegraph/scip](https://github.com/sourcegraph/scip)). Read directly from `scip.proto`: `Index` → `Document` → `Occurrence`/`SymbolInformation`, with a `Relationship` message (`symbol` plus `is_reference`/`is_implementation`/`is_type_definition`/`is_definition` booleans) that is a real structural match for monokl's trait-impl use case — the proto's own worked TypeScript example (`Dog#` relationships to `Animal#`) is exactly this. No confidence/ precision field exists anywhere in the schema. The moniker grammar (`<scheme> <package> <descriptor>+`, with `.` as an explicit "empty" placeholder for manager/package-name/version) is more forgiving than it first looks but still buys monokl nothing over its existing internal keys. Checked the actual Rust producer: rust-analyzer's SCIP CLI (`crates/rust-analyzer/src/cli/scip.rs`, `compute_symbol_info`) hardcodes `relationships: Vec::new()` — today's de facto "scip-rust" emits zero implementation/override relationships, so there is no real SCIP data to consume yet for monokl's first target. Indexer maturity is real and active for TypeScript/Python/Java (`scip-typescript` v0.4.0 Oct 2025; `scip-java` 775 commits/30 contributors; `scip-python` a maintained pyright fork); no standalone `scip-rust` exists beyond rust-analyzer's built-in exporter. Governance transitioned to an independent Core Steering Committee (Meta, Uber, Sourcegraph) with a formal RFC process in March 2026 — real cross-org backing. Consumption precedent is genuine but narrow: Meta's Glean ingests `scip-python` output via a converter rather than writing its own Python indexer; Mozilla's Searchfox consumes `scip-java` for Java/Kotlin alongside its own from-scratch indexer. GitLab still has no native SCIP support. An official `scip` Rust crate (v0.9.0, one real dependency `protobuf = "=3.7.2"`) makes parsing trivial if ever needed — the hard part would be semantic merging, not the wire format. See §2/§5 for the resulting adopt/reject split.

**stack-graphs / tree-sitter-graph** ([github/stack-graphs](https://github.com/github/stack-graphs)). Extends the _scope graphs_ framework (Visser et al., TU Delft) with a stack mechanism for compound references — core paper Creager, "Stack graphs: Name resolution at scale," OASIcs EVCS 2023.8 (arXiv:2211.01224). Graph construction is file-isolated (each file's subgraph built with zero cross-file visibility, joined later via partial-path stitching), which is what gives it incrementality without a daemon — architecturally compatible with monokl's daemon-free constraint, which is the one point in its favor. Against it: only four language definitions were ever built (Java, JavaScript, Python, TypeScript — none for Rust or Go), the TypeScript definition alone is 6,297 lines of a bespoke `.tsg` DSL, resolution is a binary path-exists/doesn't search with no precision-tier concept, and GitHub archived the entire repo in September 2025 with no successor ("if you wish to continue development, fork it"). Production usage was real while it lasted (GitHub's own Precise Code Navigation, Python Dec 2021 / TypeScript Mar 2024). Verdict: skip: see §5.

**ast-grep** ([ast-grep/ast-grep](https://github.com/ast-grep/ast-grep)), read end-to-end (core matcher, rule DSL, language registration, CLI worker — not just the README). A pattern is parsed by the target language's own tree-sitter grammar into a `PatternNode` tree (`convert_node_to_pattern`, `crates/core/src/matcher/pattern.rs`), then matched via a generic `Aggregator` trait implemented once for the real match environment and once for a cheap match-end-only counter — one recursive algorithm serving both "does it match" and "where does it end." The YAML rule DSL has three tiers (atomic: `pattern`/`kind`/`regex`/`nthChild`/`range`; relational: `inside`/`has`/`precedes`/`follows` with a `stopBy` and field-targeted matching via `child_by_field_id`; composite: `all`/`any`/`not`/named reusable `matches` rules with cycle detection). A `MatchStrictness` enum (`Cst/Smart/Ast/Relaxed/Signature/Template`, `crates/core/src/match_tree/strictness.rs`) tunes how literally a pattern must match, down to "text only, ignore node kind." Adding a language is a one-line macro pointed at a tree-sitter crate, with no node-kind normalization layer — rules are not portable across languages, and grammar bugs leak directly into matcher correctness (a documented tree-sitter-typescript span bug is explicitly worked around in the strictness module). Ranking and caching are both genuinely absent — grepped the whole repo for anything score/rank/relevance-shaped and found nothing; matches return in file order, and every invocation fully reparses every file with no persistent cache of any kind (mtime, content-hash, or otherwise), using `ignore::WalkParallel` rather than rayon. This is not a gap relative to monokl — ast-grep doesn't attempt ranked/semantic search at all, so BM25, dedup, and token budgeting have no ast-grep prior art to compare against, favorable or not. See §2 for the `MatchStrictness`/relational-rule adoption.

**difftastic** ([Wilfred/difftastic](https://github.com/Wilfred/difftastic)). Confirmed from the author's own writeup ("Difftastic, the Fantastic Diff") that diffing is framed as shortest-path search (Dijkstra) over a DAG of `(left_position, right_position, parent-exit-stack)` vertices built from a uniform s-expression form of each tree-sitter tree — a sequential positional alignment, not general tree-edit-distance over subtree identity. A follow-up optimization writeup ("How do I boost difftastic by 4x") shows the real engineering cost is almost entirely vertex-memory-layout work (shrinking the `Vertex` struct, pruning zero-weight-edge chains, allocator choice), not algorithm choice — A* was tried and dropped for no real improvement over Dijkstra. Move detection is explicitly unimplemented: Wilfred's own issue #508 (opened 2023) proposes it as future work and it remains open. Adding a language needs a tree-sitter grammar plus `atom_nodes` (which node kinds are leaves despite having children) and `delimiter_tokens` (paired delimiters) — real per-language tuning, misconfiguring either produces spurious diffs. Verdict: the core algorithm is overkill for monokl's actual need (semantic "what changed," not minimal general-purpose text diff); see §2/§5 for what's still worth borrowing (uniform IR, per-language leaf/delimiter config, and beating difftastic on move detection specifically since it still doesn't have any).

## 8. Literature grounding: CHA/RTA/k-CFA and points-to analysis vs. `CapabilityPrecision`

Call-graph and points-to analysis is a mature subfield with a clean precision/cost ladder that maps onto `CapabilityPrecision` (`Unsupported < Heuristic < Structural < Exact`) better than expected, with one real gap the literature exposes. All citations below were independently verified by search (title/authors/venue/page cross-checked), not recalled from memory.

**Class Hierarchy Analysis (CHA)** — Dean, Grove, Chambers, "Optimization of Object-Oriented Programs Using Static Class Hierarchy Analysis," ECOOP 1995, pp. 77-101. CHA resolves a virtual call from the declared class/interface hierarchy alone: any subtype of the static receiver type is a possible target, full stop — no dataflow, no reachability, no instantiation check. Fast, purely syntactic, known-unsound (ignores reflection, dynamic loading, generics-driven dispatch). This is `TraitImplIndex`'s (§2) shape exactly: it indexes every `impl Trait for Type` from the AST with no check on whether `Type` is ever constructed — a declared-hierarchy fact, not a program-behavior fact. `Structural` is a correct label for this.

**Rapid Type Analysis (RTA)** — Bacon & Sweeney, "Fast Static Analysis of C++ Virtual Function Calls," OOPSLA 1996, pp. 324-341. RTA refines CHA with one extra static pass: track which classes are actually instantiated (`new`) anywhere in the reachable program and prune CHA's target set to those. On their benchmarks (7 C++ programs, 5-20 KLOC) this resolved 71% of virtual calls statically, vs. CHA's much larger over-approximation. Critically, RTA is still single-pass, non-iterative, and needs no aliasing or points-to information — it costs the same order as CHA, not the order of a real type checker. That means RTA is not a stand-in for `Exact`; it is a finer-grained rung _inside_ what monokl currently collapses into one `Structural` tier. Concretely: CHA-shaped = "declared hierarchy says `Type` could implement `Trait`"; RTA-shaped = "...and `Type` is actually constructed somewhere in this corpus." An RTA-style filter over `TraitImplIndex` (§2) — cross-referencing implementor types against observed struct-literal/constructor sites, already information monokl's `SymbolIndex` pass collects — is a legitimate, still-`Structural`-cost enhancement worth recording, not a new precision tier.

**k-CFA** — Shivers, "Control-Flow Analysis of Higher-Order Languages, or Taming Lambda," PhD thesis, CMU-CS-91-145, May 1991 (formalizing the earlier "Control-Flow Analysis in Scheme," PLDI 1988, pp. 164-174). k-CFA answers a different question than CHA/RTA: not "which subtype could this be" but "which closure could this call site invoke," by abstracting environments to k-deep call-string contexts. It is EXPTIME-hard for any static k>0 — Van Horn & Mairson, "Deciding kCFA is complete for EXPTIME," ICFP 2008, pp. 275-282 — and the blow-up is fundamental, not an implementation artifact (companion result: Might, Smaragdakis, Van Horn, "Resolving and Exploiting the k-CFA Paradox," PLDI 2010, showing even k=1 degenerates badly on OO-flavored code specifically because class-based dispatch, monokl's actual target, isn't what k-CFA's context-sensitivity is built to disambiguate). k-CFA is the wrong shape and the wrong cost class for monokl: it targets first-class-closure flow in dynamically-typed/functional code, not "what implements this interface" or "what does this import resolve to." Tellingly, even IDE-scale JS tooling built for monokl's actual problem class explicitly avoids it — Feldthaus, Schäfer, Sridharan, Dolby, Tip, "Efficient Construction of Approximate Call Graphs for JavaScript IDE Services," ICSE 2013, use a cheaper field-based approximate analysis instead of full k-CFA specifically to hit interactive latency. Verdict: k-CFA is correctly out of scope (§5); no part of this spec should be revised toward it.

**Points-to analysis** — the two foundational styles: Andersen, "Program Analysis and Specialization for the C Programming Language," PhD thesis, DIKU, University of Copenhagen, 1994 (inclusion-based/subset-constraint, more precise, worse complexity); Steensgaard, "Points-to Analysis in Almost Linear Time," POPL 1996, pp. 32-41 (equality-based/union-find, "almost linear," less precise). Bravenboer & Smaragdakis, "Strictly Declarative Specification of Sophisticated Points-to Analyses," OOPSLA 2009 (the Doop framework), show Andersen-style points-to specified in Datalog scales across a dial of context-sensitivity (context-insensitive up to k-object-sensitive) rather than being one fixed cost point — the literature's actual answer for what a non-`ra_ap_hir` path toward `Exact` looks like, relevant to the open Salsa/persistent-daemon track (§4) as a second candidate design, not just `ra_ap_hir`.

**Recent IDE-scale precedent.** PyCG (Salis, Sotiropoulos, Louridas, Spinellis, Mitropoulos, ICSE 2021, arXiv:2103.00587) — dependency-free static call-graph generation for Python — reports 99.2% precision but only 69.9% recall, concrete quantified evidence that even careful assignment-based static analysis without type inference has a real recall ceiling for a dynamic language, directly backing this doc's own admission (§04-analysis-fidelity.md, problem 5) that Python forward-reference resolution without pyright is `Heuristic`, not `Structural`. SootUp (Karakaya, Schott, Klauke, Bodden et al., TACAS 2024) modernizes Soot's engineering (lazy class loading, fail-early validation) but not its cost model — full points-to/call-graph construction there is still a batch, whole-classpath operation, reinforcing rather than challenging monokl's daemon/non-daemon split (§4). No CodeQL/Semmle paper describing an explicit graded-precision model comparable to `CapabilityPrecision` was found — de Moor et al., "Keynote Address: .QL for Source Code Analysis," SCAM 2007, pp. 3-16, describes the Datalog query engine, and CodeQL's public Java/Kotlin call-graph docs describe one virtual-dispatch-aware resolution strategy with no published notion of graded confidence tiers. Worth stating plainly rather than implying false precedent.

**Verdict:** no new `CapabilityPrecision` tier needed, and no change to k-CFA's exclusion. One concrete, low-cost documentation fix: `Structural`'s definition in §11 should note it currently spans both a CHA-shaped fact (declared-hierarchy membership) and would span an RTA-shaped fact (hierarchy-membership-plus-instantiation) if the `TraitImplIndex` instantiation filter above is ever built — both are real, distinct precision levels in the literature that this spec currently collapses into one label. That collapse is defensible as shipped (same cost order, same soundness caveats), but should be named rather than left implicit.

## 10. Generic tree-sitter fallback tier: decision and launch set

Triggered by two things landing together: real usage-ranking data (GitHub Octoverse 2025, TIOBE July 2026, Stack Overflow 2025) showing C (TIOBE #2) and C++ (TIOBE #3) both ranked above Java and completely absent from this roadmap, and a question raised back in §6 by studying codegraph but never resolved — whether monokl should add a generic, thinly-configured tree-sitter tier for languages that don't merit Go/Java-level hand-tuned investment. Kotlin and Swift (real candidates for Android/mobile reach) were evaluated as part of the same pass.

**Decision: adopt the tier.** One `LanguageAnalyzer` impl handles all of it, internally dispatching via a small per-language config table (extension → node-kind buckets), in the same spirit as codegraph's own `LanguageExtractor` interface and ast-grep's per-language registration (`impl_lang!`/`impl_lang_expando!` — a one-line macro pointed at a tree-sitter grammar crate, no cross-language node-kind normalization layer). This is one additional `AnalyzerRegistry` entry owning N languages, not N new entries — no dispatch restructuring needed. Output is capped at `Heuristic`/`Structural` precision by policy, with no bespoke `InspectEntry` classifier per language; unlike every other analyzer in this spec, `CapabilityPrecision` must be reported per-language-instance _inside_ this one impl, since different fallback-tier languages have genuinely different ceilings (see below).

**The premise this idea was sold on doesn't survive contact with the evidence, and the design has to account for that rather than assume it away.** codegraph — the tool whose 30+-language reach originally motivated this — does not actually keep its per-language config thin in production. Its own architecture docs and issue tracker show real, sustained special-casing: Kotlin needs custom nested-property-declaration visiting, Java needs Lombok-generated-member synthesis (the exact problem this spec already solved bespoke for `lang-java`), C# needs generic-unwrapping and nullable-stripping, C++ needs smart-pointer unwrapping, COBOL needs a fixed-to-free preprocessing pass before parsing even starts — and codegraph's maintainers describe this as ongoing, expected growth, not a one-time cost that levels off. "Thin config" is this idea's aspiration, not a description of what shipped multi-language tooling actually requires once real usage arrives. Consequence: any fallback-tier language that gets real traction will generate the same pressure, and it has to be actively capped by policy — the `Heuristic`/`Structural` ceiling and the no-`InspectEntry` rule above are that cap, not a suggestion to relax once a language proves popular. A language that needs more than that cap allows is a graduation candidate (see below), not a reason to widen the fallback tier's own scope.

Real precedent for the _shape_ itself, independent of codegraph's specific execution: universal- ctags already runs a structurally similar two-tier model — hand-written full parsers for complex languages, plus a genuinely generic, user-extensible regex-based "optlib" mechanism for everything else, which validates `Heuristic`-only as the honest ceiling for a truly thin tier rather than something to reach past. More importantly, Sourcegraph ships close to this exact shape in production today: fast, always-available search-based navigation (generically powered by ctags and tree-sitter) as a fallback alongside precise SCIP/LSIF navigation for repos with a real indexer — credible evidence this two-tier product shape is genuinely load-bearing, not a compromise nobody actually uses. (GitHub Linguist was checked and is _not_ real precedent here — it's heuristic pattern-matching for language identification, not AST-based code intelligence, and doesn't validate this specific tier.)

**Launch set, prioritized by the usage data**:

- **C** — clean grammar (`tree-sitter/tree-sitter-c`), mature, widely embedded elsewhere (difftastic, ast-grep, nvim-treesitter), open issues cluster on C23/C2y feature gaps rather than fundamental ambiguity. TIOBE #2.
- **C++** — TIOBE #3, a real and previously-unaddressed gap. The tree-sitter path alone launches capped at `Heuristic`, not `Structural`: `tree-sitter-cpp` issue #74 documents a genuine unresolved grammar ambiguity (statement parsing is expression-vs-declaration-ambiguous without type information that may live in headers the parser never sees), plus real bugs in `typeid`, casts, pointer-to-member, and defaulted friend operators. **Superseded in part by §12**: an optional Clang-gated analyzer clears this ambiguity for real (Clang resolves it the only way it's actually solvable — real semantic analysis inline with parsing) and is the recommended default when Clang is available, with the tree-sitter tier as the no-toolchain fallback rather than C++'s only option.
- **Bash** — mature, low-ambiguity grammar, near-universal presence as CI/build tooling across almost every real repo regardless of primary language. Cheap, low-risk.
- **C#** — grammar is real and healthy (Roslyn-grammar-derived, active maintenance through mid- 2026). This spec's earlier decision to drop C# (§6) was about bespoke-analyzer ROI specifically — that reasoning doesn't transfer to fallback-tier inclusion, since the tier explicitly skips the bespoke investment the earlier decision was weighing against.

**Held back from this tree-sitter tier specifically, not from monokl's language support overall**:

- **Kotlin** — not a maturity-over-time problem, a hard ceiling: the best available grammar (`fwcd/tree-sitter-kotlin`, actively maintained and cross-validated against JetBrains' own PSI parser) reports only 61.2% structural match against the official compiler AST in its own validation suite. A weaker competing grammar exists and is worse. Shipping _this tier_ for Kotlin today means shipping a tier whose own maintainers can't get past ~61% agreement with ground truth — don't. **§12 has a real answer for Kotlin that isn't this tier**: a JVM-subprocess compiler-PSI parse, the same mechanism ktlint/detekt use by default, clears well past this ceiling without needing a classpath.
- **Scala** — official grammar is stale (a year old) and explicitly does not support Scala 3 syntax, now the dialect most real Scala code is written in. Shipping it would mean silently misparsing the modern language, not a coverage gap that degrades gracefully. **§12 has a real answer for Scala too**, and a stronger one than Kotlin's: Scalameta, a mature JVM-subprocess parser with Scala 3 support solved since 2021-22 and a direct precedent for monokl's exact use case (`scalex`, "Scala code intelligence for coding agents. Zero Build Server. Zero Compilation.").
- **Swift** — technically fine (`alex-pinkus/tree-sitter-swift`: 4 years, 487 commits, 26+ contributors, zero open issues, used by difftastic and nvim-treesitter) but lower priority given its mobile-concentrated reach relative to C/C++/Bash/C#. Add opportunistically, not in the initial launch set.
- **Ruby, PHP** — both solid, mature, actively maintained grammars with real production tooling precedent (Ruby: GitHub semantic highlighting, difftastic, ast-grep; PHP: split into `php`/ `php_only` grammars in 2024 specifically to fix real HTML-injection conflicts for Blade/Twig templating). Reasonable second-wave adds once the initial four are shipped and the special- casing-pressure hypothesis above has been checked against reality.

**Graduation path back to a dedicated analyzer.** A fallback-tier language earns Go/Java-style bespoke investment when it clears both: (a) sustained usage in the current Go/Java tier (roughly top 10-12 on TIOBE/Octoverse) _and_ (b) documented evidence of a structural-precision ceiling analogous to Java's Lombok problem — idioms common enough in real code that `Heuristic`/ `Structural`-only output silently breaks call-chain or symbol resolution for a large fraction of real codebases. **C++ already clears both today**, and §12 answers what that graduation actually looks like: not a from-scratch native-Rust parser (mirroring OXC/`gosyn`/`ra_ap_syntax` turned out to be the wrong shape here — C++'s parsing ambiguity is a real semantic-analysis problem, not a grammar-engineering one no pure-Rust parser could plausibly solve better than tree-sitter already does), but an optional Clang-gated analyzer. See §12 for the full recommendation and for Kotlin and Scala, which have their own version of this same "held back from the tree-sitter tier, but not stuck there" story.

## 11. Parser performance: what's actually known, and what monokl's cache/benchmark plan should do about it

monokl mixes native-Rust AST parsers (OXC, `ra_ap_syntax`, `gosyn` — no FFI) with tree-sitter-via- FFI grammars (Python, Java today; C/C++/Bash/C# joining via §10's fallback tier). Nothing in this spec has ever benchmarked the difference, and the `benches/pipeline.rs` criterion groups referenced in §2 remain stubbed. This section records what real, published data does and doesn't say, so future work doesn't guess where measurement is actually required.

**What's real and citable**: OXC publishes its own parse-only benchmarks (`oxc-project/bench-javascript-parser-written-in-rust`, `iter_with_large_drop` to exclude AST- teardown cost) — concretely, `cal.com.tsx` parses in 3.4ms vs. 14.4ms for swc and 18.3ms for Biome (the Biome comparison is explicitly flagged non-apples-to-apples, CST vs. AST); `typescript.js` parses in 26.4ms vs. 91.0ms (swc) and 139.3ms (Biome). **Tree-sitter is not in OXC's own comparison set at all** — there is no published OXC-vs-tree-sitter-typescript number anywhere.

**What tree-sitter itself publishes is thin.** No official throughput figures exist. The closest data points: an informal maintainer comment (tree-sitter/tree-sitter Discussion #3413) citing a 6k-line file parsed in ~80ms by a custom grammar and a 20k-line file parsed in ~120ms by the Python grammar, presented as "comparable," not a rigorous benchmark; and, more usefully, tree-sitter/ tree-sitter issue #1277, which reports a 1.6MB JSON file taking ~1.2s for a full cold parse and **~0.7s to re-parse with zero edits**, using ~300MB for two trees. That no-op-reparse number is direct evidence that tree-sitter's incremental-parse advantage has a real floor even in its best case — it is not free.

**Where tree-sitter slowness has actually been root-caused, it's grammar-specific, not FFI- inherent.** tree-sitter-haskell's documented 50x speedup (traced independently by both the grammar author's own writeup and tree-sitter-haskell issue #41, "terrible performance on medium/big files") came from fixing an external scanner that called `malloc` per token — a C-side allocation bug in that specific grammar. Separately, Symflower's reported 36x speedup migrating from JavaParser to tree-sitter was driven by eliminating cross-process/cross-language calls, a different failure mode from Rust-to-C FFI (which is near-zero-cost via `extern "C"` — no marshaling, unlike Python `ctypes` or JNI, which do pay a real tax). **There is no evidence that `tree-sitter-python` or `tree-sitter-java` pay an FFI-crossing tax inside monokl's Rust host.** If either is slow in practice, the more likely cause per the Haskell precedent is that specific grammar's allocation behavior — discoverable only by profiling those two grammars directly, not inferable from the FFI boundary alone.

**Real gaps, stated plainly rather than papered over.** No published head-to-head benchmark exists for `ra_ap_syntax` vs. `tree-sitter-rust`, a native Go parser vs. `tree-sitter-go`, or any Python native-parser candidate vs. `tree-sitter-python` (Ruff's own parser-evolution writeup benchmarks only against its own predecessor, never against tree-sitter). `gosyn` publishes zero benchmark numbers. Among comparable tools already researched in this log: ast-grep's own "10x faster" writeup attributes its win entirely to regex-cloning and `potential_kinds`-matching fixes, saying nothing about parse-cost scaling; difftastic's "4x faster" writeup confirms its bottleneck was `Vertex`/diff-graph memory layout, not parsing, but never publishes a parse-time-vs-diff-time split; codegraph reports ~60 files/sec end-to-end (parse+extract+write combined, no per-language breakdown) — extrapolated naively, that's ~167s for 10k files, which should make this spec's own existing ~15s cold-build target read as unvalidated and plausibly optimistic, not as a number any of this research should be used to relax.

**Verdict and what changes in this spec**:

- No public evidence justifies differentiating cache-tier treatment by parser type on FFI-crossing grounds. If a specific tree-sitter grammar turns out to be slow for monokl, that's a per-grammar profiling finding, not a general FFI cost monokl should design around preemptively.
- Tree-sitter's incremental-reparse advantage is close to irrelevant to monokl's own architecture and should not factor into planning: monokl is a fresh process per invocation reading from cache, never holding a previous tree to diff against, so it always pays the cold-parse path regardless of what any grammar's incremental mode can do. Budget every tree-sitter-backed language (present and any §10 fallback-tier addition) at cold-parse cost — for the `OneShot` lifetime. Part 8's `Session` lifetime holds the previous tree and is the one case where this should be re-measured (§15(b)).
- Memory is a real open question, not a closed one: the one available data point (a 1.6MB JSON file consuming ~300MB across two trees) suggests tree-sitter's transient peak during parsing can be nontrivial, and no fleet-scale (10k-50k file) comparison against native parsers exists publicly. Given this spec's own arena-containment rule (no borrowed AST data may escape a per-file `analyze()` call — every `FileAnalysis` must be owned), the actual risk is the transient peak during conversion to owned data, not steady-state footprint — worth a targeted monokl-internal check once real code exists, not something to resolve from public data.
- Do not port any number surveyed above into `benches/pipeline.rs` as a target threshold — none are methodology-comparable to monokl's own file mix (see §2's cross-reference). The only trustworthy fix is running the existing stubbed benchmark groups against monokl's own fixtures.

## 12. Beyond tree-sitter's ceiling: a real-compiler-frontend tier for C/C++, Kotlin, Scala

§10 capped C++ at `Heuristic` and held Kotlin and Scala back from the fallback tier entirely, each for a real, language-specific ceiling: `tree-sitter-cpp`'s documented parsing ambiguity, `tree-sitter-kotlin`'s 61.2% structural-match ceiling against the real compiler AST, and `tree-sitter-scala`'s missing Scala 3 support. This section asks the follow-up question directly: is there a better answer than living with those ceilings, short of the full daemon/session-mode investment already deferred for `ra_ap_hir`? For all three languages, yes — a real middle tier exists, cheaper than a daemon and meaningfully better than tree-sitter, though it takes a different shape per ecosystem.

**C and C++: an optional Clang-gated analyzer, not a bespoke native-Rust parser.** `libclang` FFI bindings are real and heavily precedented — `clang-sys` is what `bindgen` itself depends on — but the friction is real too, not hypothetical: `bindgen`'s own docs require Clang 9.0+ and document `LIBCLANG_PATH`/`llvm-config` discovery explicitly, and a cluster of live issues (rust-bindgen#1797, #2091, #1276, #1579, #2360, #1411; `clang-sys`#74; `actions/runner-images`#3316) show "could not find libclang" failures spanning Windows, Docker, Alpine, and CI runners — a well-worn pain point for exactly the "cargo install and it just works" experience the rest of this spec's parser choices protect. A better-fitting crate exists for monokl's actual need: **`clang-ast`** (dtolnay, actively maintained, 575k downloads) doesn't link `libclang` at all — it shells out to `clang -Xclang -ast-dump=json -fsyntax-only` and deserializes the JSON into typed structs. That's a strictly lighter integration surface: no header/version matching, no `dlopen` path-hunting, just "is `clang`/`clang++` on `PATH`."

The compilation-database problem (real semantic analysis needs real include paths and macros, normally from `compile_commands.json`) degrades gracefully rather than failing outright — clangd's own docs confirm it falls back to generic default flags and a documented degraded mode when no compilation database exists. More useful: **`-frecovery-ast`** (RecoveryExpr) has been on by default in Clang since version 11 (2020) specifically so clangd keeps working on broken/WIP code — it preserves AST nodes across semantic errors (unresolved identifiers, overload failures, missing members). This is Clang's own team already solving, at the semantic layer, the exact "tolerate broken code" problem tree-sitter structurally cannot touch since it has no semantic layer at all. The win is bounded, though: RecoveryExpr only helps once a file is found and parsed — a missing `#include` is a preprocessor-level fatal error with no equivalent recovery flag, a real and frequently-reported complaint (clangd#695 and others). So Clang clears `Heuristic` easily for self-contained or system-header-only files; for header-heavy real-world C++ lacking real include paths, it's back near tree-sitter's ceiling.

A pure-Rust alternative was checked for C specifically (C++ is a harder case, addressed below): `lang-c` (vickenty) claims "almost full C11" support, but was last _published_ to crates.io in September 2023 despite GitHub commits as recently as October 2025 — two years of merged-but- unreleased work, a real single-maintainer bus-factor signal. It's built on `rust-peg`, which has no built-in error-recovery machinery (an open, unshipped feature request, kevinmehall/rust-peg#276) — the same fail-fast risk that already ruled out `syn` for Rust in this spec (§3). No other credible pure-Rust C parser exists on crates.io. **Recommendation: don't build a bespoke native-Rust analyzer for C either** — ride it on the same optional Clang tier as C++, since C has none of C++'s ambiguity problem, making the incremental cost of covering it near zero once the C++ tier exists.

C++'s specific ambiguity is confirmed structurally unsolvable by any heuristic approach, not just under-engineered: `tree-sitter-cpp`#74's example (`a * b;` as multiplication vs. a pointer declaration) requires knowing whether `a` names a type, which requires a live symbol table during parsing — real semantic analysis, the thing Clang/GCC do and tree-sitter structurally cannot. **Decision**: add an optional, runtime-detected analyzer for C and C++ via `clang-ast`'s subprocess approach, capped at `Structural` (not `Exact`) without a real compilation database, falling back automatically to §10's tree-sitter tier when Clang isn't found on the host.

**Kotlin and Scala: an optional JVM-subprocess compiler-parse tier, distinct from the daemon question.** Both languages' real "compiler as a library" story turned out more nuanced than a flat "daemon-only." For Kotlin: `kotlin-compiler-embeddable` (what `detekt`/`ktlint` historically used) is being abandoned — it's incompatible with the newer Analysis API, confirmed by detekt's own migration issue (detekt#8027, closed May 2026). The hoped-for lighter K2 frontend for external tools does not exist yet either — JetBrains' own docs state standalone mode "is currently in development and subject to incompatible changes," with IntelliJ plugin development the only officially supported use case today. But a real, production-proven middle ground already exists independent of both of those: `ktlint` and `detekt`'s **default** (non-type-resolution) mode runs directly on the compiler's real PSI tree and needs no classpath at all — "parsing a Kotlin file does not require any knowledge about the project it belongs to," per their own docs. That's real compiler-grade parsing, clearing well past tree-sitter's 61.2% ceiling, at the cost of a JVM subprocess rather than an in-process library call. `detekt`'s further opt-in type-resolution tier (needs `--classpath`) is the genuine daemon-territory tier, same shape as Java's `jdtls` — that part of the original assumption holds unchanged.

For Scala, the case is stronger. **Scalameta** is mature, actively maintained, and — critically — its Scala 3 support is a closed, years-old problem rather than an open gap: the tracking issue (scalameta/scalameta#2022, opened 2020) closed in 2021, with the last edge case (#2315) closed in 2022, and Scalafmt has shipped `dialect = scala3` support since v3.0.0 in real production use. This directly contrasts with `tree-sitter-scala`'s own Scala 3 issue, open since 2021 with no maintainer response — a structural gap for tree-sitter specifically, not a general "Scala 3 tooling is immature" problem. Scalameta's parse-only cost is real and lightweight (~92k lines/sec, ~1.4MB per 100k LOC), and there is a direct precedent for monokl's exact use case: **`scalex`** (nguyenyou/scalex, actively maintained) is explicitly built as "Scala code intelligence for coding agents. Zero Build Server. Zero Compilation," using Scalameta parse-only and documenting the identical precision tradeoff this spec already cares about verbatim — real numbers of 18.5k files/144k symbols in 2.7s cold / 349ms warm. One more mitigation unique to Scala: `scalafmt- native-image` (scala-cli/scalafmt-native-image) proves Scalameta-based tools can be compiled via GraalVM native-image, avoiding the JVM cold-start tax entirely — no confirmed Kotlin equivalent exists. Real semantic Scala (SemanticDB) still requires actual compilation via a `scalac`/`dotc` plugin, the same daemon-territory tier as `ra_ap_hir`/`jdtls`, unchanged.

No pure-Rust or WASM alternative exists for either language worth considering (checked directly on crates.io: Kotlin has only a WIP `kotlin-parser` at v0.0.2 plus the tree-sitter grammars already evaluated; Scala has no real parser crate at all).

**Decision**: add an optional JVM-subprocess `Structural`-tier analyzer for Kotlin (compiler PSI, no classpath) and Scala (Scalameta, no classpath) — a genuinely new middle rung distinct from both the in-process tree-sitter tier and the deferred daemon/session-mode track, not a substitute for either. Scala's case is evidence-stronger than Kotlin's (solved Scala 3 support, a native-image cold-start mitigation, and a direct real-world precedent in `scalex`); Kotlin's standalone Analysis API being explicitly unstable per JetBrains' own docs means its long-term story may still shift. True semantic/`Exact`-tier resolution for both — real classpath construction, real type information — stays on the same deferred daemon track as `ra_ap_hir` (§4); this section adds a rung below that, not a way around it.

## 14. Daemon/session-mode architecture — moved to Part 6

The open daemon/session-mode question (§4) got a dedicated, research-backed design pass: a 16-agent workflow (9 per-language backend studies — TypeScript, Rust, Python, Go, Java, Kotlin, Scala, C/C++, and a combined C#/Ruby/PHP pass — 3 cross-cutting architecture questions, 3 adversarial critiques of a draft design, and one synthesis) stress-tested a proposed `PrecisionUpgrader` trait against how real semantic backends for every language on this roadmap actually behave, rather than designing it in the abstract. The result is substantial enough to need its own file rather than another entry here, per this log's own convention for substantial changes: see **[06-daemon-architecture.md](./06-daemon-architecture.md)** for the full design — the trait shape, the lifetime model (and why it needs to nest and distinguish owned-vs-attached), the `DaemonExtension` ingestion model, a `PrecisionLedger` for attaching confidence after the fact (eagerly, lazily, or retroactively, decoupled from `FileAnalysis`'s own cache lifecycle), confidence-signaling rules, and the per-language lifetime table.

Headline result, in brief: the core shape survived (every backend maps onto `PerCall`/ `PerInvocation`/`Session` as a real cost ceiling, no language demanded a fourth tier), but the trait's _return type_ did not — five independent per-language studies (Kotlin, Go, Scala, Rust, C++) converged on the same finding that "promote a bare `CapabilityPrecision`" destroys real candidate sets, dual precision axes, and structured facts the underlying tools actually hand back. Also produced: real backend identification per language (`typescript-go`/TS 7.0's new LSP server went GA July 8, 2026, superseding the plain-tsserver assumption; Python's `Pyrefly`/`ty` are genuinely Rust-implemented but still subprocess/LSP-integrated, not embeddable libraries; Java's `jdtls` import step hard-crashes via OOM past ~3000 files, a real gate requirement, not a graceful degradation; Kotlin's `kotlin-lsp` is real but still built on the same unstable-per-JetBrains foundation already flagged, just hidden behind a heavier IDE-embedding shell); and a confirmed, structural gap in both LSP and SCIP — neither protocol carries a confidence field, so the compilers' own internal degradation signals (Clang's `RecoveryExpr`, JDT's `isRecovered()`) have to be recovered via a per-backend sentinel table, not trusted from protocol silence.

A follow-on, three-thread research pass (academic ML-confidence literature, real shipped tools' confidence practices, runtime/implementation options) then asked the question underneath all of this: how should `PrecisionAnnotation` values actually get computed, not just where they live. All three threads converged independently on the same answer, now recorded in [06-daemon-architecture.md §7](./06-daemon-architecture.md): don't build a live per-instance numeric confidence score — every real ML type-inference system checked (DeepTyper, TypeWriter, Type4Py, HiTyper, OptTyper) either skips calibration or shows a real confidence/accuracy gap in its own published numbers, and every one still gates its statistical signal with an independent symbolic check regardless, the same pattern §6's sentinel design already uses. Every real shipped tool checked (CodeQL's `@precision`, Semgrep's `confidence`) stays categorical and rule-level, and Google's Tricorder (the one fully-verified production feedback mechanism, full paper read directly) tunes reliability _per analyzer_ via a slow accept/reject ratio, never per finding. Concrete result: a small deterministic ordinal downgrade lattice (categorical tier in, secondary signals only ever downgrade, real cross-tier agreement can counteract one step) — with real 20-year-old precedent for this exact combination shape in program analysis specifically (Kremenek & Engler's Z-Ranking, SAS 2003) — rather than a trained model or a probability shown to agents.

result: Fourteen research threads' worth of findings applied or recorded, plus one dedicated architecture design pass split into its own file: three direct spec fixes (including the `LanguageAnalyzer` trait's `language_id`/`capabilities` signatures, a real compile-correctness gap §10's own fallback tier exposed), eleven adopted-but-unbuilt changes, three validated-as-is decisions, three open investigation tracks (one of which — daemon/session-mode — now has a full design in Part 6, including a `PrecisionLedger` for attaching confidence after the fact), five explicit rejections, an updated language roadmap now including a decided (not just proposed) generic tree-sitter fallback tier plus a real-compiler-frontend tier above it for C/C++/Kotlin/Scala, a literature-grounding pass tying `CapabilityPrecision` to the CHA/RTA/k-CFA/points-to canon, a verified 12-repo eval-harness corpus (two miscategorizations and one unconfirmable proposal caught and corrected in the verification pass, not just rubber-stamped), a parser-performance survey that found real gaps in public data rather than fabricating numbers to fill them, and the daemon-architecture design in [06-daemon-architecture.md](./06-daemon-architecture.md). ## 15. Library session API, batch queries, identity — moved to Part 8

Wisp will embed monokl in-process, and the free-function API in Part 1 cannot serve it: every `pipeline::*` call rebuilds its own analyzer, `dependents` rebuilds the whole `WorkspaceIndex`, `build` is `pub(crate)` and flushes the disk cache on every call, and the symbol/dependents caps plus their English truncation strings live inside the analysis layer. A six-track research pass (session/snapshot API design, symbol identity and provenance, empirical context-selection studies, incremental/scoped indexing, batch-query and tool-surface design, artifact freshness) checked a set of proposed changes against primary sources rather than adopting them on argument. The resulting design is **[08-library-session-api.md](./08-library-session-api.md)**. Decisions adopted there, one line each:

- **`Workspace` (mutable, `!Clone`) + `Snapshot` (immutable, `Clone + Send + Sync + 'static`)** — rust-analyzer's `AnalysisHost`/`Analysis` split (`crates/ide/src/lib.rs`); Biome's `&self`-everywhere `Workspace` trait was considered and rejected because it reintroduces retry-on-pending-write at every call site (`crates/biome_service/src/workspace.rs`).
- **No cancellation** — rust-analyzer cancels because Salsa's memo table is shared mutable storage and a write waits for readers to die (`docs/book/src/contributing/architecture.md`; `ty`'s `trigger_cancellation` in `crates/ty_project/src/db.rs`). Monokl's index is immutable after build; `apply_change` swaps an `Arc`, old snapshots go stale, `Snapshot::is_current` says so. Removes `Cancellable<T>`, `catch_unwind`, and `UnwindSafe` bounds from the API.
- **`Lifetime::{OneShot, Session}`** on `WorkspaceOptions` — `ty` is a one-shot CLI that still builds a session database and then calls `disable_lru` + `freeze` (`crates/ty/src/lib.rs`).
- **`apply_change(Change)` with `FileContent::{Reread, Text, Deleted}`**, content-hash-gated at the source, Create/Delete distinguished from Modify — rust-analyzer's `FileChange` (`crates/base-db/src/change.rs`) and VFS `Change::{Create, Modify, Delete}` with `has_structure_changes` (`crates/vfs/src/lib.rs`, `global_state.rs`).
- **`FileIdx` stops being observable** — prerequisite for both scoped open and cheap invalidation; positional indices make scoped and full opens incomparable and turn any create/delete into a full enricher rebuild. Consistent with §2's earlier rejection of SCIP's moniker grammar *as a `FileIdx` replacement*: the SCIP grammar is adopted for the public identity string only, `FileIdx` stays a dense internal offset.
- **`Scope::{Complete, Partial}` as a completeness axis orthogonal to precision**; reverse-closure ops (`dependents`, `refs`) return `Unsupported` under `Partial`, never a silent under-approximation — Kythe bundles required inputs per compilation unit; TypeScript project references document Find-All-References as a non-feature across boundaries; `cargo check -p` never checks dependents. Default `hops = 1`: RepoGraph's ablation (arXiv 2410.14684) shows 2-hop flattened (26.00%) below the no-graph baseline (27.33%), 1-hop flattened at 29.67%.
- **Lazy enrichers via `OnceLock`** — "it's not the incrementality that makes an IDE fast, it's laziness" (rust-analyzer, *Three Architectures for a Responsive IDE*).
- **`WorkspaceFingerprint { durable, volatile }`** — Salsa's durability tiers as a version vector, without Salsa (rust-analyzer, *Durable Incrementality*: ~300ms recovered per local edit).
- **`Snapshot::query(&QueryRequest) -> QueryResponse`** with index-parallel `Vec<OpOutcome>` (DataLoader's ordering contract), one `BudgetReport`, one `Provenance`, `Detail::{Lite, Full}` degrade-before-drop (LSP 3.17 `workspaceSymbol/resolve`), and a `deadline`. Justification is intermediate results never entering model context (Anthropic, *code execution with MCP*: 150k → 2k tokens) and snapshot atomicity, not the shared budget. Neither LSP (Base Protocol 0.9 line 122) nor MCP (2025-11-25 tools spec) batches at the protocol level, so batching can only live inside one call.
- **`monokl-core` / `monokl-agent` crate split**; caps and truncation strings leave core; BM25 ranking stays — rust-analyzer's `ide` invariants ("LSP does not influence its API design"; "don't make it serializable, create a serializable counterpart") and `git(1)`'s plumbing/porcelain stability rationale.
- **`SymbolId` SCIP-compatible at the string, not the container**; no path, no kind, no line in identity; `Local` derived from scope structure rather than SCIP's per-document counter — `scip.proto` lines 157–179, `docs/DESIGN.md` ("not meant as a storage format for querying"), rust-analyzer `cli/scip.rs` (`local_count` reset per document; four `FIXME` tests for nested items).
- **`Provenance { agent, activity, inputs, workspace, scope, precision }`** with `provenance_is_current` as Glean's derived-fact conjunction rule (`glean.software/docs/implementation/incrementality`); PROV-DM's Agent/Activity/used structure borrowed, its vocabulary not.
- **Per-edge precision**, projected at query time from the Part 6 `PrecisionLedger`; ambiguous resolution is a candidate set (already argued in 06 §2). Verified by full read of `scip.proto` (962 lines): no confidence field on `Occurrence`, `Relationship`, `SymbolInformation`, or `Index`; LSIF, Kythe, Glean have none either. Part 6's claim stands.
- **`Digest` on the OCI descriptor grammar** (`algorithm ":" encoded`, registered `sha256`/`sha512`/`blake3`, lowercase hex mandatory) — internal keys stay `blake3:`, interchange is `sha256:` because sha256 is in Node `crypto`, Python `hashlib`, and `sha256sum`, and blake3 is in none of them (checked locally). The bare-hex `ContentHash(String)` was unmigratable.
- **`wisp-contracts`** holds vocabulary only, permissively licensed. Whether `SymbolId`'s grammar belongs in it is an open licensing question.
- **SCIP roles `Generated` and `Test` carried on occurrences** — the only provenance-flavoured bits SCIP has.
- **Benchmarks extended** with an incremental condition, Create/Delete vs Modify split, refold-vs-parse split, stale-snapshot RSS, and budget-policy comparison.

### 15.1 Round-two amendments

- **License changed from AGPL-3.0-or-later to FSL-1.1-MIT, 2026-09-04.** Suite consistency with Wisp and Lumen; removes the FSL-linking-AGPL redistribution conflict noted in Part 8 §11.2. See Part 8 §11.2 for the updated statement.

A second research pass, run after Part 8 was written, resolved four things Part 8 left contradictory or unstated. Each is applied in Part 8 at the section named.

- **The budget seam: core measures, the caller budgets** (Part 8 §7.3–§7.5, §9.1). Part 8 put `budget: Budget` and `policy: BudgetPolicy` on `monokl-core`'s `QueryRequest` while §9.1 put `Budget`, `BudgetPolicy`, `apply_budget`, and tiktoken in `monokl-agent`, and §7.2's own flow diagram labelled `apply_budget` a `monokl-agent` step inside `Snapshot::query` — a `monokl-core` method. Resolved by taking §9.1 literally: core returns fully ranked, uncapped results plus `cost: Vec<OpCost>` under a `Limits` memory ceiling, and every budget is allocated one layer up by two peer allocators, `monokl-agent` for the CLI and Wisp's `wisp-context` for a briefing. Three alternatives were rejected on evidence: a caller-supplied `measure` closure has no digest and so breaks `OperationId::normalized_params` and `provenance_is_current`; a fixed tokens-per-byte constant is either a 3.8x overrun risk (measured 3.78 bytes/token on Rust source, adversarial worst case 1.0) or the byte bound with extra ceremony; and a core-side token budget forces the caller to guess a code sub-budget before knowing what its other sections cost, reintroducing the round trip §7.1 cites Anthropic's *code execution with MCP* result to eliminate. `SkipReason::BudgetExhausted` is deleted; `SkipReason` and `Detail` are otherwise unchanged, and `Detail` gains the acceptance criterion `lite(full(x)) == lite_direct(x)` without which caller-side degrade is unsound.
- **Byte length is a proven upper bound on token count** (Part 8 §9.1). All 256 single-byte tokens are present in both `cl100k_base` (100,256 entries) and `o200k_base` (199,998 entries), verified locally; BPE never splits below a byte and every merge strictly reduces the count, so a *k*-byte pretoken encodes to 1..=*k* tokens, and the measured worst case across all probes is exactly 1.000 tokens per byte, never above. §7.4's prefilter instruction is therefore exact with zero false negatives rather than a heuristic. Two `tiktoken-rs` hazards measured alongside it: `cl100k_base()` rebuilds the BPE table on every call (29–38 ms; `o200k_base()` 64.5 ms) and only the `*_singleton()` variants cache, and `byte_pair_merge` is O(n²) in pretoken length — 200 KB of one unbroken run takes 8.59 s.
- **`wisp-contracts` type shapes, aligned** (Part 8 §5.1, §6, §8.1, §8.2, §11). Five shapes in Part 8 could not survive the wire format they were specified for. `scheme: &'static str` cannot be deserialized without leaking, so it and `PackageId`/`Descriptor`'s `SmolStr` fields become `String` (`smol_str` is also a `0.x` public dependency in a crate whose job is stability). `Scope::Partial` hoists its payload into a `#[non_exhaustive]` `PartialScope` struct, because adding a field to an enum variant is a major change even on a `#[non_exhaustive]` enum, per the Cargo SemVer reference. `WorkspaceFingerprint`'s two `u64` fields serialize as 16-character hex strings, because a `u64` exceeds JavaScript's `Number.MAX_SAFE_INTEGER` and is silently rounded by every Node consumer including michi's NAPI surface, and a rounded fingerprint never compares equal. `observed_at` becomes `ObservedAt(i64)` epoch milliseconds, because serde renders `SystemTime` as a two-field `secs`/`nanos` object. Counts are `u64` rather than `usize`, which is platform-dependent and meaningless in JSON. `Budget` joins `BudgetReport`, `OpBudget`, `OpCost`, and `SkipReason` in contracts, since `BudgetReport.limits` is a `Budget` and could not compile there otherwise; `BudgetPolicy` and `apply_budget` stay in `monokl-agent` as policy and behavior. §9.1's diagram listed the Wisp Plugins artifact schemas under contracts, contradicting §11's own prose and Wisp D-010; corrected.
- **Threading and the stale-snapshot bound** (Part 8 §2.2, §2.4, §3.2). `Workspace` is `Send` and deliberately **not** `Sync`, so "two threads share one `Workspace`" is a compile error and the owner-thread arrangement holds by construction; this requires `Box<dyn LanguageAnalyzer + Send>` in `AnalyzerRegistry`. The embedder-side shape is an actor thread owning the `Workspace` by value with the current `Snapshot` published beside it, request-scoped `!Clone` snapshot leases, and a fixed pool of `min(available_parallelism(), 4)` — rust-analyzer (`config.rs:2784-2792`), `ty`, and `ruff` (`crates/ty/src/lib.rs:31-36`) all run analysis on a hand-rolled fixed pool with no async runtime beneath it, and there is no tokio anywhere in the ruff repository. `tokio::task::spawn_blocking` is rejected on tokio's own documentation: the pool defaults to 512 threads and is sized for I/O (`builder.rs:306`), its queue applies no backpressure (`builder.rs:544-549`), and a blocking task cannot be aborted so shutdown waits for an in-flight cold open (`blocking.rs:107-120`). From a non-rayon thread, `rayon_core::Registry::in_worker` injects the job and parks the caller on a latch contributing no work (`registry.rs:516-540`), so each concurrent call costs a parked thread plus the rayon pool's own. §3.2's unbounded stale-snapshot memory is therefore the embedder's bound, and it is `1 + pool_size`: five live revisions at a pool of 4, against 513 under a default blocking pool — 450–700 MB versus 46–72 GB at 50k files. §13's stale-snapshot benchmark now reports resident bytes per pinned revision so an embedder can multiply by its own bound, and the incremental benchmark uses a 28-op batch, the size a real briefing issues, rather than 10.
- **Relationship to the gated specs** (Part 8 §14). Part 8 was written without reading `.claude/specs` and `.claude/plans`, which predate it by one to three weeks. Two conflict. SPEC-011 locks `ContentHash(String)` as bare blake3 hex and explicitly declines deserialize-time validation; §8.4's `Digest` supersedes it, and it needs a correction pass before code is written against it — a plan landing on bare hex writes cache entries that must later be migrated. SPEC-004 locks a single-crate `monokl` manifest, which is correct for its own stated v0.1.0 baseline and is not the target shape; the `monokl-core`/`monokl-agent` split needs a follow-on spec rather than an undo. SPEC-005, SPEC-009, and SPEC-010 are orthogonal or agree. Tracks 20 and 21 have not started and should be drafted against Part 8 directly, so no rework arises.

## 16. Building for real, and the orin-dx conventions (2026-10-21)

The crate could not build: `io-errors` came from a private `orin-cargo` registry that nothing configured, and `lib.rs` and `Cargo.toml` declared 12 modules, a binary and a bench with no file behind them. These changes depart from Part 1's verbatim §1, §2, §27 and §28 text, which has not been rewritten to match yet.

- **`FileIoError` is `monokl::file_io`, not the `io-errors` crate.** §27's contents are unchanged; only the home moved. No private registry. See [ADR 0001](../adr/0001-file-io-error-lives-in-monokl.md).
- **Declare as implemented.** `lib.rs` declares only modules with a file, `Cargo.toml` lists only dependencies code uses, and `[[bin]]`/`[[bench]]` return with `main.rs` and the benchmark. The `lang-ts` feature goes with the OXC dependencies it gated and returns with `TsAnalyzer`. `[workspace.dependencies]` keeps the full version catalogue.
- **Versions.** oxc 0.128 to 0.151, dashmap 5 to 6.1, criterion 0.7 to 0.8, insta 1.47 to 1.48, matching caliper.
- **Toolchain.** proto pins Rust 1.98.1 in `.prototools`; `rust-toolchain.toml` and its `wasm32-unknown-unknown` target are gone, since nothing builds for wasm. MSRV stays 1.96 and CI checks it.
- **Lints.** Added rustc `unused_must_use` and `let_underscore_drop`, and clippy `let_underscore_must_use`, `let_underscore_untyped` and `map_err_ignore`, all deny. rustfmt `max_width` is 120.
- **Releases.** Callisto 0.14.0 (pinned in `.prototools`) owns versioning: `callisto.toml`, `.changeset/`, a generated `callisto-release.yml`, and a CI Changesets check. `monokl` stays `publish = false`, so nothing releases until that is a deliberate change.
- **Organization.** orin-axi is now orin-dx: repository URLs and the npm scope (`@orin-dx/monokl`).
- **michi from crates.io.** michi is `michi-core` 0.7.1 from crates.io, renamed to `michi` in `Cargo.toml` so code paths are unchanged. The git pin it replaces was AGPL-3.0-or-later. michi now escapes line breaks itself (TOON 4.4), so `cell` no longer pre-escapes them; null and empty-string cells now render distinctly (`null` vs `""`). An error's source chain goes into michi's `causes` via `DomainError::from_error`, not into hints, and a multi-line message stays whole.
